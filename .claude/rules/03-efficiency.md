# 执行效率与工程纪律

## 执行效率铁律（2026-10-29 实测得出）

本节基于一次 2 小时 7 分钟会话的日志分析：136 条命令实际执行合计约 148 秒（2%），其余 7842 秒全部花在模型思考、代码生成和排查意外上。以下四条针对的是那 98%。

1. **先认环境的命令拦截规则，别撞墙**
   - 运行环境的 hook 会拦截看起来危险或涉及全局变更的命令：删除类操作（含命令行里的 `delete` / `drop`）、`npm i -g`、`mise use|install|upgrade`、全局包安装。
   - 需要清理测试数据时，优先用项目内带 `--apply` 开关的维护脚本，或先写临时文件再执行；不要把 `delete` 语句直接拼进命令行。
   - 撞到拦截后**不要连续试变体**（换引号、拆命令、换 shell），直接换一条根本不同的实现路径。实测这一类试错平均一次吃掉 3-7 分钟。

2. **测试断言先查真实数据**
   - 写数量类断言前先查一遍实际数据。静态 DC/SA/CR/CW 自带默认壳用例，断言"用例数 = 2"这类最容易踩。
   - 断言失败时**先怀疑断言写错，再怀疑产品代码**。实测一次此类排查花掉 13 分钟。

3. **大任务按可交付单元拆开**
   - 多视图、多模块的功能按"一个视图一个完整闭环"拆：实现 → 验证 → 提交 → 汇报。
   - 不要把三个视图塞进同一个 turn。上下文变长后重复读同一批文件的概率明显上升。

4. **避免重复读取**
   - 同一文件在同一个 turn 内读第二次之前先确认必要性，多数时候前文已经有过。
   - 本次会话 136 条命令中有 62 条是读代码，其中相当一部分是重复读。

这四条的目的不是省事，而是把时间从"撞墙和返工"转移到"实现和验证"。

## 禁止操作

1. 禁止为了省事把新接口堆进单个大文件；API 按业务域拆分。
2. 禁止把 HTML 转 OOXML 作为 Word 生成主方案。
3. 禁止在 MCP 截图/浏览器工具可用时手写自动化脚本；手写兑底仅限当前会话无对应 MCP 时，且必须使用本机 Edge channel 截图，不下载独立 Chromium，不用 DOM 文本断言替代视觉验收。
4. 禁止把终端执行器设为 `bash`，或在 PowerShell 命令中混用 bash 语法；长命令与交互命令走 Terminal 面板或显式 `pwsh`。

## 整理铁律

每完成一块功能，必须做一次 scoped 整理：

1. 删除本次产生的无用文件、临时文件、重复资源和死代码。
2. 精简并去重相关 MD；需求进 `srs/`，坑位进 `docs/项目记忆.md`，操作入口进 README，不重复堆内容。
3. 新增代码超过单文件职责、或继续往页面/大服务里堆逻辑时，按业务域、组件、API、仓储和样式分层拆分。
4. 检查目录命名、模块边界和公共抽象；只有重复或复杂度真实出现时才抽公共层。
5. 整理后必须跑对应验证；涉及文档与结构时检查链接和引用。

连续做多块功能时，在准备结束会话时主动提醒用户：“本次会话累计了多块功能，建议下班前做一次全局整理。”
