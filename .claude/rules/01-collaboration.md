# 协作规则

1. 始终使用简体中文回复；README、架构设计、API 文档全部中文。
2. 每次会话开工先读取 [srs/12-跨会话记忆.md](../../srs/12-跨会话记忆.md)，恢复上次会话的任务与偏好。
3. 需求、模块边界和未确定事项先维护到 `srs/`，入口是 [srs/README.md](../../srs/README.md)。
4. 可复用坑位只记录到 [docs/项目记忆.md](../../docs/项目记忆.md)，格式固定为“现象、原因、规避方式”。
5. 浏览器视觉验证默认使用视觉模型：直接生成截图并查看截图，不再要求用户切换模型，也不再把 DOM 文本断言作为视觉验收结论。

   **验证分级（2026-10-28 新增）**：浏览器与功能验证按改动范围选档，禁止无差别全量跑。
   - **冒烟档**：每次改完必跑。后端 `go test ./... -count=1` + `go vet ./...` + 构建；前端 `npm run check`；浏览器只走改动直接影响的 1-2 个页面。
   - **全量档**：仅在发版前、用户明确说"全面验证"、或说"下班"时执行。全部页面 + 全量接口冒烟 + Markdown 链接检查。
   - 汇报必须写明跑的是哪档、覆盖了哪些页面，不许含糊。
6. 用户说“下班”时：先跑当前改动对应验证，再检查 `git status`，只提交本次相关文件，Commit 信息用中文，最后执行 `git push origin`；同时列出本次会话实际使用的 skills，检查其可用更新并提醒用户决定由代理更新还是用户更新，未获明确决定前不得升级、重装或删除 skills。验证失败或无远端时说明原因并停止。

8. 用户说“开始工作”或要求打开前后端时：启动前必须分别检查全部后端 Go 依赖库（含 Huma v2、GORM、SQLite 驱动等）和全部前端 npm 依赖库是否有可用更新；有更新时升级到兼容的最新稳定版，更新 `go.mod`、`go.sum`、`package.json` 和 `package-lock.json`，完成对应构建或依赖一致性验证后再启动；无更新时直接构建启动或确认服务可用。启动阶段不扩展业务测试，由用户自行验证并反馈问题，收到问题再处理。
9. 尽量使用最新工具链与环境：PowerShell 7（pwsh）+ Windows Terminal，命令示例优先 pwsh 语法；文本检索用 ripgrep（rg）。
10. 必须看本文档的前端铁律，必须使用组件库。
11. 能用 MCP 坚决用 MCP：浏览器截图、视觉验证等任务开工先检查可用的 MCP 工具；能用就用。浏览器任务优先使用 Claude Desktop 内置浏览器面板（`preview_*` 工具）；只有确实没有可用的应用内浏览器时，才回退 Playwright MCP（本机 Edge channel），并且必须在汇报里写明回退原因和已尝试的方式。仅当当前会话确实没有对应 MCP 工具时，才允许手写兜底脚本，且必须说明原因。Playwright 不用于替代截图视觉判断。
12. 技术选型铁律：能使用成熟组件、成熟库或成熟方案，就必须使用，禁止先手搓。开发前先检查项目内已有封装，再搜索并核对官方文档、成熟开源库和主流生态方案；只有确无满足需求的成熟能力，或成熟方案需要过度改造时，才允许局部手写，并把原因、边界和验证方式记录到对应 SRS。
13. 浏览器自动化验证默认使用路由拦截夹具或专用测试项目，禁止在真实项目数据上触发保存、删除或状态变更；确需真实数据验证时必须先向用户说明范围并获得确认。
14. 终端执行器铁律（零容忍）：本项目运行在 Windows + PowerShell 环境，所有终端命令必须使用 `pwsh` 语义。Claude Desktop 会话中长命令和交互命令走 Terminal 面板（`run_in_terminal`，PowerShell）或显式 `pwsh`，Bash 工具仅用于只读短查询。除非用户明确要求 POSIX、Git Bash 或 WSL，禁止使用 bash 专用语法，禁止在同一条命令中混用 bash 与 PowerShell（包括把 bash 管道接到 `Select-Object` 等 PowerShell 命令）。每次执行前必须先自检 shell；发现不是 `pwsh` 语义立即拒绝并重写调用，不得执行。误用后必须停止、说明该命令未执行，并立即用 `pwsh` 重跑；不得以复制示例、惯性或疏忽为理由再次发生。
15. **实现自主、需求止步**：SRS、交接文件和现有代码中的实现方案仅作参考，有更合理方案可直接调整并说明理由；可搜索并借鉴真实产品与设计案例优化布局、视觉层级、交互、空状态、加载态和错误提示，汇报时说明参考对象、选择原因及与原方案的差异。功能范围、字段口径、业务规则、验收标准、数据权限属于需求边界，必须由用户确认；无法判断时按需求处理并先问，禁止自行拍板。
