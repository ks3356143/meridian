# 接收文件与版本

> 返回 [大工作区架构落地](../20-大工作区架构落地.md)

## 接收文件录入作业流

第一版已经进入真实接口落地。用户拿到一批接收文件后的动作顺序如下：

1. 选择或拖入多个文件，也允许手工登记尚未拿到电子文件的资料。
2. 系统按文件名和扩展名预识别工作对象类型、版本和解析方式；平台由项目平台自动派生。
3. 用户补齐接收日期、提供方、接收方式，并可批量应用到待确认行。
4. 用户逐行或批量确认登记。确认后的行成为工作对象版本，`.doc` 标记需转 `.docx`，主 SRS 可为同版本补传 DOCX 解析副本，代码包只登记版本和来源。
5. 确认后进入需求与追踪模块做解析确认；同文名新版本后续进入版本比对，不直接覆盖旧版。

工作对象类型第一版包含：软件需求规格说明、系统规格说明、研制总要求、软件研制任务书、技术要求、用户手册、代码包、其他依据资料。用户手册只做资料和版本登记，不进入软件需求解析。

平台存储口径中，项目“CPU/非嵌”派生为 `cpu`，项目 `FPGA` 派生为 `fpga`。历史数据中的 `common` 仅作为兼容值保留，不再在新登记中生成。前后端和数据库必须使用同一套对象类型枚举值，前端不得把后端下划线枚举改成连字符。

同版本识别口径：项目 + 对象类型 + 规范化对象名称定位唯一 `work_object`；`work_object` + 版本号定位唯一版本。同一对象同版本重复上传时，无论文件内容是否相同，都返回 409 冲突，不覆盖已有版本。待确认版本可以删除后重传；已确认版本录入错误通过登记纠错处理，版本演进通过更高版本建立版本链，资料失效用作废。文件名变化但对象类型、对象名称和版本不变时，仍视为同版本冲突。

录入表格必须支持批量选择、行内编辑、重复文件提示、删除待确认行和已确认行移出待确认队列。对象名称、类型、版本、来源、接收日期是确认前的必看字段；其中对象名称、类型、版本、来源不允许为空。平台不在表格中展示和编辑。上传的原始文件名只作资产信息展示，不作为业务对象名称的权威值。非待确认版本在接收队列中只读。批量上传在任一文件校验、落盘或入库失败时，必须回收本批次已经落盘的文件；行内编辑保存失败时必须回滚该字段的显示值，不得让用户误以为已保存。
录入表格必须使用行级 memo 和稳定回调；一个行内字段输入时，未变更行不得重渲染。若默认浅比较因数据对象或回调引用失效，应使用只比较渲染输出字段的行级比较器。

### 真实存储与 API

文件存储根目录由配置指定，默认 `data/file-assets/`。数据库保存业务关系，文件目录保存原始文件；两者必须一起备份。

```text
data/file-assets/
  projects/
    {projectCode}/
      {workObjectId}/
        {versionId}/
          {assetId}.original.ext
```

数据表：

- `work_objects`：项目内的工作对象定义，按对象类型和名称唯一。
- `work_object_versions`：工作对象版本、状态、项目派生平台、提供方、接收日期和接收方式。
- `received_assets`：原始文件名、存储路径、大小、类型、SHA-256 和上传人。
- `work_object_lifecycle_events`：确认、替代、撤回、恢复、作废的操作原因、操作人和时间。
- `requirement_sections`：SRS 版本内的章节树，按来源版本和章节号唯一。
- `software_requirements`：软件需求登记信息、候选/正式/排除/替代状态、原文锚点和测试项待创建契约。
- `requirement_events`：需求创建、修改、解析、确认和排除审计。

第一版 API：

| 方法 | 路径 | 职责 |
| --- | --- | --- |
| POST | `/api/v1/projects/{code}/work-objects/upload` | multipart 批量上传，服务端识别对象类型和版本，平台按项目派生，生成待确认版本。 |
| POST | `/api/v1/projects/{code}/work-objects/manual` | 手工登记没有电子文件的工作对象版本。 |
| GET | `/api/v1/projects/{code}/work-objects` | 返回项目全部工作对象版本及资产摘要。 |
| PUT | `/api/v1/work-object-versions/{id}` | 修改对象名称、类型、版本和接收信息；已确认版本必须携带 `correctionReason`，作为登记纠错处理。平台由系统保持项目派生值。 |
| POST | `/api/v1/work-object-versions/{id}/confirm` | 确认为正式工作对象版本。 |
| POST | `/api/v1/work-object-versions/{id}/parse-copy` | 为已确认 `.doc` 主 SRS 补传同版本 DOCX 解析副本。 |
| POST | `/api/v1/work-object-versions/{id}/withdraw` | 撤回当前确认，必要时自动恢复被替代旧版本。 |
| POST | `/api/v1/work-object-versions/{id}/revoke` | 作废当前确认版本，保留文件与审计记录。 |
| GET | `/api/v1/work-object-versions/{id}/lifecycle` | 查询生命周期审计记录。 |
| DELETE | `/api/v1/work-object-versions/{id}` | 删除未使用版本；同时间删除对应文件。 |
| GET | `/api/v1/projects/{code}/requirements` | 查询已确认主 SRS、章节树和软件需求。 |
| POST | `/api/v1/projects/{code}/requirement-sections` | 手工新增 SRS 章节。 |
| POST | `/api/v1/projects/{code}/requirements` | 手工保存正式软件需求。 |
| POST | `/api/v1/projects/{code}/requirements/bulk` | 批量粘贴预览确认后保存章节和需求。 |
| POST | `/api/v1/projects/{code}/requirements/parse` | 解析当前已确认主 SRS 的 DOCX，生成候选需求。 |
| PUT | `/api/v1/software-requirements/{id}` | 修改候选或正式需求并写入审计。 |
| POST | `/api/v1/projects/{code}/requirements/status` | 批量确认或排除需求。 |

上传即创建草稿并落盘，确认前允许修正字段；同名同版本重复上传返回冲突，不静默覆盖。后续 V1.00 -> V1.01 通过同一 `work_object_id` 建立版本链。
只有待确认版本允许删除；删除前必须弹出确认框，明确说明会同时删除数据库记录和接收文件。已确认版本不能从接收队列直接删除，后续如需作废应走带权限和原因的作废流程。

### 版本生命周期

工作对象版本状态分为四态：

| 状态 | 含义 | 可编辑 | 可删除 | 参与有效基线 |
| --- | --- | --- | --- | --- |
| `draft` | 待确认 | 是 | 是，二次确认后物理删除 | 否 |
| `confirmed` | 当前有效版本 | 仅允许通过登记纠错修改名称、类型、版本和接收信息，必须填写原因并写入生命周期审计；平台不可纠错 | 否 | 是 |
| `superseded` | 已被新版本替代 | 否 | 否 | 否，仅历史追溯 |
| `revoked` | 已作废 | 否 | 否 | 否，仅历史追溯 |

规则：

1. 确认新版本时，同一工作对象下原 `confirmed` 版本自动转为 `superseded`，记录替代版本 ID。
2. 撤回当前确认版本时，该版本回到 `draft`；如果它替代过旧版本，自动将最近的旧版本恢复为 `confirmed`。
3. 作废当前确认版本时，该版本转为 `revoked`，数据库记录和原始文件都保留。
4. 撤回和作废必须填写原因，并保存操作人、时间、状态迁移和原因。
5. 只有 `draft` 版本允许直接修改业务字段和物理删除；`confirmed` 版本发现录入错误时使用登记纠错，必须填写原因，状态不变、原始文件和哈希不变，并记录 `correct` 生命周期事件。
6. 登记纠错至少要改变一个登记字段；完全相同的值返回 400，不产生生命周期事件。
7. 登记纠错只用于修正录入信息，不用于表达资料失效或版本演进；资料失效使用作废，版本演进使用新版本确认。后续接入需求、测试项和文档引用后，纠错前必须检查引用关系并展示影响范围。
