# 大工作区架构落地

## 状态

- 本文件记录大工作区从 0 重设计后的架构落地版本。
- 当前处于第二轮架构骨架评审期：界面使用静态架构数据展示信息结构，后端模型和真实 API 尚未接入。
- 用户每轮评审意见先更新本文件，再同步修改对应前端模块，避免讨论结论散落在对话中。

## 已定架构口径

1. 大工作区是项目作业系统，不是文档编辑器。
2. 项目数据是唯一权威；任务视图是入口；时间口径与 Word 都属于生成阶段投影。
3. 阶段是推荐路径，不是强制流程。允许先生成后续文档、先创建后续轮次、后补前置数据。
4. 项目不预设“系统 / 分系统 / 配置项”权威层级。用户在测试项章节中自建组织树，可以用这些名称做文件夹，但它们不是项目的强制实体层级。
5. 主数据链采用：项目 -> 工作对象 -> 软件需求 -> 测试项 -> 测试用例 -> 问题单。轮次是执行与回归分组，问题单与用例多对多。
6. 平台是数据适用维度，不做全局切换器。需求、测试项、用例可标记公共、CPU、FPGA 等平台。
7. 需求与测试项分离，追踪关系独立建模；测试项组织树承接章节结构、测试类型和执行入口。
8. 四类静态测试拥有专属流程，但不默认“静态先行”。静态与动态测试都在测试项树中实施，实际先后由项目情况决定。
9. 轮次不做全局顶栏切换，只在“测试与执行”模块的轮次上下文中切换和联动。

## 三棵树分离

### 1. 资料与工作对象

工作对象是项目接收和分析的对象，不要求先形成被测层级。类型至少包含软件需求规格说明、系统规格说明、研制总要求、研制任务书、技术要求、代码包和后续补充资料。工作对象负责版本、来源、接收时间和解析结果；需求归属于产生它的工作对象版本，代码包可以不产生软件需求，但允许作为静态测试项的追踪目标。

### 2. 测试项组织树

测试项组织树服务大纲测试项章节、测试说明编制和执行入口，允许用户自由创建文件夹。典型结构可以是：

```text
XXX分系统
  XXX配置项A
    文档审查
    静态分析
    代码审查
    功能测试
      XXX功能
        XXX子功能
    接口测试
  XXX配置项B
```

节点性质分为组织文件夹、测试项、测试子项。文件夹可带“分系统、配置项、功能域”等语义标签，但语义标签不改变数据所有权。静态测试项选中后进入 DC / SA / CR / CW 专属流程；动态测试项选中后进入用例设计与执行流程。

### 3. 文档输出树

文档输出树由生成时的输出范围决定，不从测试项组织树强行推导。客户要求一个分系统 7 个配置项出一份文档时，同一份 7+2N 文档在大纲章节中展开这些文件夹；客户要求分开展出时，同一棵测试项树通过输出范围和聚合方式生成多份文档。

## 主数据模型

| 层级 | 核心字段与关系 |
| --- | --- |
| 项目 | 委托、平台、等级、成员和配置容器。 |
| 工作对象 | 类型、名称、版本、来源、接收信息、文件或代码包资产。 |
| 软件需求 | 章节号、名称、描述、需求类型、平台、来源工作对象版本。 |
| 测试项 | 组织节点、测试类型、标识、方法、追踪关系、充分性和通过准则。 |
| 测试用例 | 默认由测试子项生成，允许合并、拆分和手工创建；随轮次形成执行实例。 |
| 问题单 | 与测试用例多对多，记录影响域、处理意见和回归结果。 |

顶层需求与软件需求之间的追踪、隐含需求创建、版本差异采纳，在需求模块中处理，不要求用户先把项目整理成固定层级。

## 接收文件录入作业流

第一版已经进入真实接口落地。用户拿到一批接收文件后的动作顺序如下：

1. 选择或拖入多个文件，也允许手工登记尚未拿到电子文件的资料。
2. 系统按文件名和扩展名预识别工作对象类型、版本、平台和解析方式；待确认状态下字段允许用户修改。
3. 用户补齐接收日期、提供方、接收方式，并可批量应用到待确认行。
4. 用户逐行或批量确认登记。确认后的行成为工作对象版本，`.doc` 标记需转 `.docx`，文档类标记可进入需求解析，代码包只登记版本和来源。
5. 确认后进入需求与追踪模块做解析确认；同文名新版本后续进入版本比对，不直接覆盖旧版。

工作对象类型第一版包含：软件需求规格说明、系统规格说明、研制总要求、软件研制任务书、技术要求、代码包、其他依据资料。

平台展示口径中，CPU 类工作对象显示为“CPU/其他”。前后端和数据库必须使用同一套对象类型枚举值，前端不得把后端下划线枚举改成连字符。

录入表格必须支持批量选择、行内编辑、重复文件提示、删除待确认行和已确认行移出待确认队列。对象名称、类型、版本、平台、来源、接收日期是确认前的必看字段；其中对象名称、类型、版本、来源不允许为空。上传的原始文件名只作资产信息展示，不作为业务对象名称的权威值。非待确认版本在接收队列中只读。

### 真实存储与 API

文件存储根目录由配置指定，默认 `data/file-assets/`。数据库保存业务关系，文件目录保存原始文件；两者必须一起备份。

```text
data/file-assets/
  projects/
    {projectCode}/
      {workObjectId}/
        {versionId}/
          {assetId}.original.ext
```

数据表：

- `work_objects`：项目内的工作对象定义，按对象类型和名称唯一。
- `work_object_versions`：工作对象版本、状态、平台、提供方、接收日期和接收方式。
- `received_assets`：原始文件名、存储路径、大小、类型、SHA-256 和上传人。
- `work_object_lifecycle_events`：确认、替代、撤回、恢复、作废的操作原因、操作人和时间。

第一版 API：

| 方法 | 路径 | 职责 |
| --- | --- | --- |
| POST | `/api/v1/projects/{code}/work-objects/upload` | multipart 批量上传，服务端识别对象类型、版本和平台，生成待确认版本。 |
| POST | `/api/v1/projects/{code}/work-objects/manual` | 手工登记没有电子文件的工作对象版本。 |
| GET | `/api/v1/projects/{code}/work-objects` | 返回项目全部工作对象版本及资产摘要。 |
| PUT | `/api/v1/work-object-versions/{id}` | 修改对象名称、类型、版本、平台和接收信息。 |
| POST | `/api/v1/work-object-versions/{id}/confirm` | 确认为正式工作对象版本。 |
| POST | `/api/v1/work-object-versions/{id}/withdraw` | 撤回当前确认，必要时自动恢复被替代旧版本。 |
| POST | `/api/v1/work-object-versions/{id}/revoke` | 作废当前确认版本，保留文件与审计记录。 |
| GET | `/api/v1/work-object-versions/{id}/lifecycle` | 查询生命周期审计记录。 |
| DELETE | `/api/v1/work-object-versions/{id}` | 删除未使用版本；同时间删除对应文件。 |

上传即创建草稿并落盘，确认前允许修正字段；同名同版本重复上传返回冲突，不静默覆盖。后续 V1.00 -> V1.01 通过同一 `work_object_id` 建立版本链。
只有待确认版本允许删除；删除前必须弹出确认框，明确说明会同时删除数据库记录和接收文件。已确认版本不能从接收队列直接删除，后续如需作废应走带权限和原因的作废流程。

### 版本生命周期

工作对象版本状态分为四态：

| 状态 | 含义 | 可编辑 | 可删除 | 参与有效基线 |
| --- | --- | --- | --- | --- |
| `draft` | 待确认 | 是 | 是，二次确认后物理删除 | 否 |
| `confirmed` | 当前有效版本 | 否 | 否 | 是 |
| `superseded` | 已被新版本替代 | 否 | 否 | 否，仅历史追溯 |
| `revoked` | 已作废 | 否 | 否 | 否，仅历史追溯 |

规则：

1. 确认新版本时，同一工作对象下原 `confirmed` 版本自动转为 `superseded`，记录替代版本 ID。
2. 撤回当前确认版本时，该版本回到 `draft`；如果它替代过旧版本，自动将最近的旧版本恢复为 `confirmed`。
3. 作废当前确认版本时，该版本转为 `revoked`，数据库记录和原始文件都保留。
4. 撤回和作废必须填写原因，并保存操作人、时间、状态迁移和原因。
5. 只有 `draft` 版本允许修改业务字段和物理删除；后续接入需求、测试项和文档引用后，撤回前还必须检查引用关系并展示影响范围。

## 时间口径

1. 时间不是作业前置模块，而是文档生成阶段的口径计算能力。
2. 业务数据只保留事实时间，例如接收时间、创建时间、执行时间、闭环时间。
3. 交付文档中的封面、拟制、校对、审核、批准、章节叙述、记录和问题闭环等展示时间，由生成向导根据用户给定锚点和规则统一试算。
4. 生成测评大纲时，必须保证大纲内部全部时间槽位自洽；后续说明、记录、报告生成时再按当前锚点重新试算全量时间。
5. 时间方案随文档版本形成快照。数据或锚点变化后，不静默修改已生成文档，只标记过期并提示重新生成。

## 一级导航

一级导航固定为五组，项目设置不占一级导航：

| 导航 | 责任 |
| --- | --- |
| 作业台 | 当前任务、准备度、阶段概览、阻塞项。 |
| 资料与对象 | 工作对象、接收文件、文档版本、代码包。 |
| 需求与追踪 | 需求池、导入工作台、版本比对、追踪矩阵、平台覆盖。 |
| 测试与执行 | 测试项组织树、静态测试流程、用例、轮次、测试记录、问题单。 |
| 交付与文档 | 文档生成、时间口径试算、生成历史、快照过期状态。 |

首屏为作业台，显示当前任务，不自动跳转大纲。大纲编制是作业台中的任务簇，可通过任务按钮进入。

## 前端结构

```text
web/src/features/projects/components/project-workspace/
  project-workspace-layout.tsx
  architecture/
    model.ts
    workspace-home.tsx
    components/
      current-task-panel.tsx
      test-item-tree-panel.tsx
      requirement-intake-panel.tsx
      readiness-panel.tsx
      data-flow-panel.tsx
      workspace-panel.tsx
```

职责边界：

- `project-workspace-layout.tsx` 只负责顶栏、五组一级导航、动画和路由上下文。
- `architecture/model.ts` 保存静态架构数据和任务推导规则，后续逐步替换为 API 返回模型。
- `workspace-home.tsx` 只组合首屏面板，不写具体业务表单。
- 每个面板独立文件，禁止继续把工作区首屏堆成巨型组件。
