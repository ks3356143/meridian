# 静态测试项

> 返回 [测试项与执行](../24-测试项与执行.md)

静态测试项 = 文档审查 `DC`、静态分析 `SA`、代码审查 `CR`、代码走查 `CW` 四类。它们与动态测试项共用测试项树、标识规则和用例机制，但详情工作台各自不同；**四类都不建立与单条需求的追踪关系**，只出现在测试项页。

## 一、生成与安全等级

- 项目安全等级（项目设置字段，A 最高 → D）决定静态测试项集合：

| 类型 | 触发条件 | 平台 |
| --- | --- | --- |
| `DC` 文档审查 | 全等级 | CPU / FPGA |
| `SA` 静态分析 | 全等级 | 仅 CPU / 桌面 |
| `CR` 代码审查 | C 级以上（含 C，即 A/B/C） | CPU / FPGA |
| `CW` 代码走查 | A 级以上（即 A） | CPU / FPGA |

- 触发规则（2026-10-10 定稿，按"A 最高"解读）：`DC`、`SA` 全等级；`CR` C 级以上（A/B/C）；`CW` 仅 A；D 级只做 `DC` + `SA`。
- 生成方式：项目首次进入测试项页时按安全等级创建推荐静态测试项（不覆盖既有内容）；用户主动删除后不自动回填，使用工具栏「补齐推荐静态测试项」显式补齐，或「删除全部静态测试项」清空。
- 每个静态测试项默认带 **1 条壳用例**（只存执行元数据与固定话术，不展开步骤设计），树中按普通用例显示。
- CPU / FPGA 共用同一套字段，话术与表单项按平台切换（FPGA 无 `SA`）。
- **默认测试方法（2026-10-10 用户要求 + 老项目原文）**：`DC`/`SA`/`CR`/`CW` 在 `test_item_types` 里各带一段 `default_test_method`（`CR` 另有 FPGA 变体 `default_test_method_fpga`），创建静态测试项时**自动种入 1 条子项**（名称 = `{类型名}方法`，描述 = 该段原文），详情页开箱即用、可自由改拆；历史静态测试项在进入测试项页时**懒补齐**（幂等，已有子项的不覆盖）。

## 二、DC 文档审查

> 2026-11-03 按用户要求与老项目重写（依据：老项目线上系统、`prototype-design-dc.md` §3.1–3.9）。旧版“未审→通过→不通过逐项点选、仅第 1 轮、无立单”作废。

### 结构

```text
Hero：标识 + 名称 + 状态 + 配置进度（N/7，可点击展开详情）
  └ 统计：审查单 N · 已审查 N/N · 通过率 N% · 第 N 轮
基本信息（默认收起）：需求描述 / 测试方法 / 充分性要求 / 通过准则
Tab 1 受审文档：清单表格 + 添加 / 补齐推荐文档（按平台）
Tab 2 审查单：卡片网格（多张可同时展开）+ 检查项表格
```

- 配置检查 7 项：审查单已绑定文档类型、受审文档 ≥1、审查单 ≥1、审查单已指定受审文档、所有审查单已开始审查、所有审查项已出结果、通过率 ≥80%。
- 审查单卡片显示文档类型、名称、使用版本、已审/总数、通过/不通过/不适用计数；点击展开多开，不做单开手风琴。

### 审查单模板（管理员配置）

- 工作台可配置 **5 类审查文档**：需求规格说明、详细设计、概要设计、用户手册（仅被测软件有界面）、任务书；模板字段包含文档类型、当前使用版本、检查项、依据与做法。
- **齐套性不进入 UI**：设置页与工作台都不出现，只在 Word 渲染时统一输出“全部通过”。
- 模板由管理员在「设置 → 审查单配置」维护，可增删模板与检查项、编辑富文本做法；详见 [07 审查单模板与问题单闭环](07-审查单模板与问题单闭环.md)。
- 同一文档类型只允许一个模板；版本在设置页切换，新项目创建时自动应用该版本，已有项目保持创建时的版本快照。
- 新建 DC 工作台只自动生成“需求规格说明”审查单，其余类型由测试人员从已配置模板中添加，一张模板只生成一张审查单。

### 受审文档

- 文档字典 14 项，按平台过滤：CPU 12 项、FPGA 13 项、桌面 13 项（`软件用户手册`仅桌面，`固件保障手册`仅 FPGA）。
- 可删除、添加自定义文档、一键补齐当前平台推荐文档；删除需二次确认。

### 结果与判定

- 结果三态：`通过 / 不通过 / 不适用`，点击循环 `通过 → 不通过 → 不适用 → 通过`；**新建审查单、复制轮次时全部默认「通过」**，测试人员只挑有问题的项改成「不通过」。
- 判「不通过」时展开行内编辑区：错误描述（必填）、截图证据（最多 9 张，可预览与删除）、「立单」按钮（见 07）。不通过项在表格和审查单卡片上显示红色状态。
- 每项可展开「参考做法」：仅推荐 → 绿色 ✓，仅不推荐 → 红色 ✗，两者都有 → 蓝色 ℹ，未配置 → 灰色 —；展开显示双栏富文本，未配置的项不显示入口。
- 「全部通过」批量置为通过；当前有不通过项时先二次确认，确认后清空错误描述与截图证据。
- 进度口径：已出结果的检查项 / 总检查项；通过率 = 通过项 / 总检查项；树上徽章显示 `已审 N/N`，另显示用例状态维度（与审查进度互不影响）。完成度上，DC 进入即视为完成（默认全部通过），只有存在不通过项时才算未完善。

### 与用例的快速带入

- DC 壳用例（`文档审查执行`，第 2 轮起为 `文档审查执行（复审）`）步骤的「实际结果」编辑时，工具栏出现「同步审查单」按钮，仅在当前轮存在不通过项时显示。
- 弹窗列出当前轮全部不通过项（所属审查单、检查项、序号、错误描述、截图张数），点击一项把「文字摘要 + 截图」插入当前步骤，可连续插入多项；插入后仍按步骤保存。

### 轮次

- DC 每轮都存在；新建第 2 轮及以后时自动创建一份空工作台（结果默认通过）。上轮不通过记录不自动带入，需在新建轮次向导勾选「导入上轮文档审查不通过记录」，勾选后才作为历史参考带入。
- 勾选导入上轮记录后，带入项只作历史参考，本轮默认「通过」，复审用例综述写「前一轮文档问题全部解决」；详细规则见 [05 轮次树与轮次复制](05-轮次树与轮次复制.md)。

## 三、SA 静态分析（仅 CPU / 桌面）

四张固定表单（来自测评大纲附录 C），**手风琴单开**：

| 表单 | 内容 | 第一版口径 |
| --- | --- | --- |
| C.1 代码质量度量 | 6 个基础字段 + 6 个度量元（平均规模 ≤200 行、平均扇出 ≤7、平均圈复杂度 ≤10、最大圈复杂度 ≤80、圈复杂度 ≥20 占比 ≤20%、注释率 ≥20%） | **需录入**：填实测值后按阈值自动判定"满足 / 不满足"；未录入计入完成度 |
| C.2 代码编码规则 | 152 条规则（C 13 组 + C++ 9 组，共 22 组，取自大纲附录 C.2） | **默认全部通过**，点选可标违规；违规必填原因 + 可选位置；支持整组通过 |
| C.3 控制流分析 | 11 项检查要求 + 问题记录 + 分析结论 | **默认无问题**，可切换发现问题 |
| C.4 数据流分析 | 7 项检查要求 + 同上 | 同 C.3 |

- 规则表按 22 组折叠分组，支持组级"整组通过"；长列表虚拟滚动；切换状态只重渲当前行，避免失焦。
- 壳用例步骤的"实际结果"提供"同步违规项"，把 C.2 违规 / C.3 / C.4 问题项注入文本框。
- 代码质量度量报表输出与统计口径后续再定（待讨论第 4 条）。

## 四、CR 代码审查（CPU / FPGA）

- 审查目标：默认空，用户点"添加审查目标"选语言（C / C++ / Java → CPU；Verilog / VHDL → FPGA）与审查单；可添加多个目标。
- 检查项：类别自由填写（不设枚举），做法字段富文本 + 代码块；状态三态循环（未审 → 通过 → 不通过），`不通过`可填备注并立单。
- 需求描述 / 测试方法 / 充分性要求 / 通过准则 / 用例综述五个字段按平台切换话术；用户改过的不再被平台切换覆盖。
- 树徽章显示 `已审 / 总项`。

## 五、CW 代码走查（CPU / FPGA）

- 没有审查单；核心是"源代码文件清单"表格（序号 / 文件 / 行数），支持增删行与批量粘贴。
- 走查结论与问题记录写入壳用例的步骤（人工走查记录），树徽章显示文件数。
- 与 CR 的区别：CR 按审查单逐项 check；CW 按代码执行路径人工走查，不做逐项判定。

## 六、当前实现

- **数据与口径**：静态工作台存 `static_test_workbenches.payload_json`，以版本号做乐观并发控制；项目首次生成状态存 `project_static_seeds`。迁移 `0026_static_test_workbenches`。
- **API**：`GET/PUT /api/v1/test-items/{id}/static-workbench`、`POST /api/v1/projects/{code}/static-items/ensure`、`DELETE /api/v1/projects/{code}/static-items`。保存冲突返回 409。
- **前端**：`StaticWorkbenchSection` 按 DC/SA/CR/CW 路由到专属组件；650ms 防抖自动保存并串行排队，切换测试项时补存最后一次输入；树徽章显示 DC/CR `已审/总数`、CW 文件数。
- **内置目录**：`static_catalog.json` 嵌入构建，包含 4 张文档审查单（齐套性仅保留数据、不在 UI 暴露）、75 项 C 代码审查、152 条编码规则、C.3 11 项、C.4 7 项；C++ 与 HDL 使用同类平台适配审查单。

### DC 文档审查

- 模板与文档字典按 5 类审查文档维护（需求规格说明、详细设计、概要设计、用户手册、任务书），齐套性不进入 UI，只在 Word 渲染时默认通过；14 项文档字典按 CPU 12 / FPGA 13 / 桌面 13 过滤。模板数据、版本与页面入口见 [07 审查单模板与问题单闭环](07-审查单模板与问题单闭环.md)，本文不重复。
- 结果默认「通过」，三态改为 `通过 / 不通过 / 不适用`；迁移 `0030` 把既有 `unreviewed` 批量改为 `passed`，迁移 `0031` 增加 `document_type/document_version`。
- 不通过项行内展开：错误描述、最多 9 张截图（复用项目附件接口）、立问题单（问题单为独立记录，不改变审查结果）；参考做法列支持三类状态与展开查看。
- 静态工作台新增 `images / carriedFromPrevious / previousNote / previousImages` 字段（`issueId` 为历史兼容字段，不用于状态展示）；每项截图上限 9 张由服务端校验。
- 新接口：`GET/POST/PUT/DELETE /api/v1/review-checklists`、`GET/POST /api/v1/projects/{code}/issues`、`GET/PATCH /api/v1/issues/{id}`（`import-previous` 接口保留但不在 UI 暴露）。
- 轮次：DC 每轮自动创建空工作台；勾选导入上轮记录时壳用例更名「文档审查执行（复审）」并写「前一轮文档问题全部解决」，带入项默认通过。
- 页面：受审文档清单为表格（# / 名称 / 版本 / 类别 / 操作），单元格垂直居中、短列水平居中；配置、审查单、参考做法与历史/证据行统一 0.24s 展开收起。SA 规则组切换、违规字段、CR 审查目标、CW 文件行补 0.18–0.22s 入场，结果三态按钮补颜色过渡。
- 用例快速带入：DC 壳用例步骤「实际结果」工具栏提供「同步审查单」，勾选不通过项后插入文字与截图；新建 DC 的壳用例自动带 3 条复审步骤（齐套性/需求规格/设计文档），历史空步骤用例在随轮复制时补齐。

## 八、静态四类默认内容口径（2026-10-10 定稿，迁移 0024）

新建静态测试项时由类型种子自动带入，用户在详情页可直接改：

| 字段 | 落点 | DC（文档审查）当前文案 |
| --- | --- | --- |
| 测试项描述 | `test_item_types.default_description` → 测试项 `description` | 依据测评大纲附录A中规定的文档审查要求，对被测软件交付的文档进行审查，验证文档的齐套性、规范性、准确性和一致性。 |
| 默认子项名称 | `default_sub_item_name`（缺省回落 `<类型名>方法`） | 文档审查 |
| 默认子项描述 | `default_sub_item_desc` | 留空（子项描述按需手填） |
| 操作步骤 | `default_test_method` / `default_test_method_fpga`（FPGA 项目优先） | 迁移 0022 的文档审查方法原文 |
| 通过准则 | `default_expected` | 1）被测软件文档种类齐全…2）需求文档…3）设计说明文档… |

- 其它静态类（SA / CR / CW）结构相同：测试方法文案进“操作步骤”，名称缺省 `<类型名>方法`，描述与通过准则留空待补。
- 历史数据：迁移只修正“名称 = 文档审查方法、操作步骤与通过准则都为空”的旧默认子项，并回填空描述的 DC 测试项描述；用户改过的子项一律不动。
- 待补：SA / CR / CW 的默认子项名称、描述与通过准则文案（用户后续给定后改种子）。
