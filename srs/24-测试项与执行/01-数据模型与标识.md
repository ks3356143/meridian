# 数据模型与标识

> 返回 [测试项与执行](../24-测试项与执行.md)

## 层级与术语

```text
项目
└── 测试项树（按类型分组）
    ├── 类型分组（系统按类型自动，只显示有内容的）
    │   ├── 文件夹（容器，可嵌套，无 XQ 标识 / 无用例）
    │   └── 测试项 XQ_{类型}_{后缀}
    │       ├── 测试子项（测试方法内容，不上树，无独立用例归属）
    │       └── 用例 YL_{类型}_{后缀}_{序号}
    │           └── 步骤（输入及操作 / 预期结果 / 实际结果 / 通过）
    └── 问题单（后续，暂不上树）
```

- **测试项**：独立实体，有标识、有类型、可有多个用例；一屏内完成录入与查看。
- **测试子项**：测试项"测试方法"字段的拆分内容，仅存在于测试项详情；按规范**子项与用例没有绝对关系，只有内容关系**，树上是"测试项 → 用例"。
- **文件夹**：纯容器，限装同一类型测试项，可嵌套；文件夹与测试项在同一容器内**混合排序**（同一套排序键）。
- **逻辑层 / 实例层**：测试项与用例是项目级逻辑定义；轮次通过实例引用（见 [16 轮次与追溯模型](../16-轮次与追溯模型.md)）。带入回归轮 = 同一标识的实例，人工新增 = 新标识。

## 类型字典（24 类，系统内置）

| 分组 | 类型 |
| --- | --- |
| 静态 | `DC` 文档审查、`SA` 静态分析、`CR` 代码审查、`CW` 代码走查 |
| 功能验证 | `SU` 功能测试、`IO` 接口测试、`GUI` 人机交互界面测试、`BT` 边界测试 |
| 性能强度 | `AC` 性能测试、`AT` 余量测试、`ST` 强度测试、`RL` 容量测试 |
| 环境适配 | `JR` 兼容性测试、`AZ` 安装性测试、`HZ` 互操作性测试 |
| 专项分析 | `SE` 安全性测试、`KK` 可靠性测试、`LT` 逻辑测试、`TT` 时序测试、`PA` 功耗分析、`RE` 恢复性测试、`DP` 数据处理测试 |
| 审查摸底 | `DT` 数据审查、`MD` 摸底测试 |

- 性能测试统一用 `AC`，不设 `PF`。
- 类型代号决定标识前缀、树上分组与大纲输出顺序；**第一版即落 `test_item_types` 表**（迁移 0019 种子 24 类，含各类默认充分性要求与通过准则套话），管理端配置页后续直接改表。
- 平台差异：`SA` 仅 CPU/桌面项目；`CR` CPU 与 FPGA 均建（FPGA 审 Verilog/VHDL）；`DC`/`CW` 两平台均建。平台取项目平台，测试项不单独存平台字段。

## 标识规则

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 测试项 | `XQ_{类型代号}_{后缀}`，后缀默认按名称拼音首字母生成（最多 4 位，冲突时保留前 3 位换尾字符），允许修改，项目内唯一 | `XQ_SU_ZLPA` |
| 测试子项 | `{测试项标识}_{3位序号}` | `XQ_SU_ZLPA_001` |
| 用例 | `YL_{类型代号}_{测试项后缀}_{3位序号}`，序号在测试项内自增 | `YL_SU_ZLPA_001` |
| 文件夹 | 无标识（仅名称） | — |

- 后缀字符集为大写字母与数字；改后缀时子项与用例标识同步重排。
- **自动后缀容量上限（2026-10-13 实测）**：同一名称前缀（拼音首字母前 3 位相同）最多只能自动生成 37 个后缀（原后缀 + 3 位前缀 + 36 种尾字符），第 38 个起服务端返回 400「名称前缀相同的测试项过多，标识自动生成失败；请在「新增测试项」里手工指定标识后缀」。批量录入/大纲导入前必须明确这一上限：要么在导入里自动带后缀，要么把后缀位数扩到 5 位（`identifierSuffixMax` 与 `uniqueItemSuffix` 的替换字符集同步扩位）。
- 用例序号在测试项内按顺序重编号：删除、拖拽排序、跨测试项移动后自动重排。

## 实体与关键字段

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `test_item_types` | 代号、名称、分组、静态标记、平台范围、大纲输出顺序、内置标记 | 24 类字典 |
| `test_item_folders` | 项目、类型代号、父文件夹、名称、排序键 | 可嵌套；随轮次快照带入 |
| `test_items` | 项目、标识、后缀、类型、名称、优先级、文件夹、排序键、需求描述、测试项描述、充分性要求、通过准则、隐含需求标记（`implicit_requirement`） | 项目级逻辑定义 |
| `test_sub_items` | 测试项、序号、名称、描述、操作步骤、预期结果、排序键 | 1:1 条数的操作与预期；富文本 |
| `test_cases` | 项目、测试项、标识、名称、用例综述、用例初始化、前提和约束、设计人员、执行人员、监测人员、执行时间、状态、备注、未执行原因、排序键 | 项目级逻辑定义 |
| `test_case_steps` | 用例、序号、输入及操作、预期结果、实际结果、通过状态、排序键 | 操作 / 实际为富文本内容块 |
| `requirement_test_items` | 需求、测试项 | 多对多；**DC/SA/CR/CW 不建立需求关联** |
| `round_test_items` / `round_test_cases` | 轮次、逻辑定义、来源类型（reuse / modified / new）、本轮快照与执行数据 | 见 16 |

静态测试项的专属数据见 [04 静态测试项](04-静态测试项.md)。

| 行 | 字段 | 说明 |

| 1 | 测试项名称 / 测试项标识 | 标识 = 前缀固定 + 后缀可改 |
| 2 | 优先级 | 高 / 中 / 低 |
| 3 | 追踪关系 | 第一行「关联需求」「隐含需求」操作按钮（带状态标记），第二行需求 chip 列表（带来源文档）；DC/SA/CR/CW 不显示本行 |
| 4 | 需求描述 | 手风琴列出所关联需求的章节号与描述 |
| 5 | 测试项描述 | FPGA 项目可填；CPU/桌面显示统一提示"描述见各子项卡片" |

## 用例表（详情字段顺序）

顺序按第三方测试记录 docx 的用例块对齐（`knowledge-base/参考的BCD星项目/03_...第三方测试记录V1.00.docx`，2026-10-13 二次核对），不再自拟；新建用例时综述与模板话术由后端 `caseDefaults` 默认填充：

| 行 | 字段 | 说明 |
| --- | --- | --- |
| 1 | 用例名称 / 用例标识 | 标识只读，随测试项与顺序自动重排 |
| 2 | 追踪关系 | 只读，继承所属测试项：树状目录「来源文档 → 需求（§章节号 + 名称 + 需求标识）→ 所属测试项 → 本用例」，对应 docx 的软件测试依据 / 测试需求分析 / 测试需求标识三行；静态四类不显示本行 |
| 3 | 用例综述 | 新建默认取首个子项描述，无则取测试项描述，可编辑 |
| 4 | 用例初始化 | 新建默认话术：通用「1. 被测软件已正常启动；2. 测试环境已配置就绪；3. 相关接口已连通。」；DC 为「被测文档已提交。」；SA/CR/CW 为「被测代码已提交。」 |
| 5 | 前提和约束 | 新建默认话术：通用「1. 被测软件版本受控；2. 测试环境满足设计要求。」；DC 为「提交的文档出自委托方受控库，是委托方正式签署外发的。」；SA/CR/CW 为「提交的代码出自委托方受控库。」 |
| 6 | 测试步骤 | 步骤表（见 03） |
| 7 | 执行状态 | 步骤联动只读；docx 里紧跟测试步骤，排人员之前 |
| 8 | 测试时间 | 默认当天，手动改后不再自动覆盖（手改随 5c） |
| 9 | 测试人员 | 项目成员下拉（5c 接入；docx 的"测试人员"= 库表 `tester_id`） |
| 10 | 监测人员 | 同上（`monitor_id`） |
| 11 | 问题单标识 | 只读 chip（问题单模块就绪后接入） |
| 12 | 设计人员 | 项目成员下拉（5c）；第三方测试记录 docx 无此栏位，按测试说明侧保留，排在最后 |

- 2026-10-13 按用户决定**移除「未执行原因」与「备注」两行**（库表列保留、数据不丢）；闭轮预检的"未执行原因"口径待重定。

## 状态与完善度

- 用例状态：任一"通过"步骤为**未通过** → 用例未通过；全部步骤通过 → 用例通过；其余 → 未执行 / 进行中。
- 静态类型唯一性：**一个轮次（第一版即项目）DC/SA/CR/CW 各一个**；已存在的静态类型不再出现在新增选项里，服务端同样拒绝第二个（400）。
- 隐含需求：**表示"没有可关联的需求、用户自己补的测试项"**。`implicit_requirement` 标记后按隐含需求处理——树上带琥珀色「隐含」标记，完善度的「追踪关系」按已满足计，需求描述区提示「按隐含需求处理，无需关联需求」。
- **隐含需求与需求关联互斥（前后端同源）**：已有关联需求时不能标记隐含需求（前端按钮禁用 + 悬停解释，后端 400）；已标记隐含需求时不能新增关联（前端按钮禁用，后端 400）。已同时存在的历史数据仍允许"关闭隐含需求"退出。
- 完成度（树徽章、详情提醒、保存提示同源，后端统一计算）：
  - 动态测试项：追踪关系（关联需求 ≥ 1 **或** 已标记隐含需求）、测试方法（子项）、充分性要求（FPGA 加测试项描述）。
  - `DC`：审查单 ≥ 1 且存在未出结果的检查项；`SA`：质量度量已录入；`CR`：已添加的审查目标全部有结果；`CW`：文件清单按需填写即视为完善。
  - 用例不计入测试项完成度。

## 默认话术（套话）

来源：真实交付文档《BCD星指令生成与发控软件第三方测试大纲 V1.10》（`knowledge-base/参考的BCD星项目/01-*.docx`）。套话在新建测试项时按类型预填、**允许修改**，预填后不触发"必填未填"提醒。

| 类型 | 通过准则（预填） | 充分性要求（预填） |
| --- | --- | --- |
| `DC` 文档审查 | 被测软件文档内容完整，描述准确，格式规范，文档文文一致。 | 对所有被测软件文档按照文档检查单逐项进行审查。 |
| `SA` 静态分析 | 同上（真实大纲与文档审查共用同一句） | **按源代码口径定稿**：对全部源程序进行静态分析，覆盖控制流、数据流与质量度量要求。（真实大纲原文为"对所有被测软件文档…"，判定为模板复制笔误，2026-10-10 定稿改口径） |
| `CR` 代码审查 | 代码编码符合编程准则、代码流程实现正确、代码结构设计合理，代码实现需求正确。 | 对所有软件全部源代码进行代码审查。 |
| `CW` 代码走查 | 完成要求的源代码走查，软件无走查问题。 | 按照设计的用例进行走查，形成测试记录，若发现问题提交软件问题报告单。 |
| 动态类型（`SU`/`IO`/`AC`/`BT`/`GUI`…） | 各测试步骤、测试用例执行结果与预期一致，功能实现正确。 | 测试用例覆盖所有测试子项要求的全部内容。所有用例执行完毕，对于未执行的用例说明未执行原因。 |

- 测试项描述、测试方法不套话（随项目内容写）；`SA` 的质量度量阈值、`CR` 的语言与审查单、`CW` 的文件清单另见 04。
- 与 Word 生成的关系后续单独讨论（本轮不展开）。

## 富文本字段的存储口径

- 需要富文本的字段（子项操作步骤 / 预期结果、用例步骤的操作 / 实际结果）复用现有 `content_blocks`，**不改表结构**：
  - `owner_type = 'test_item'`，`block_key = sub_item.{子项ID}.ops | sub_item.{子项ID}.exp`；
  - `owner_type = 'test_case'`，`block_key = step.{步骤ID}.op | step.{步骤ID}.act`。
- 其余字段（名称、综述、初始化、前提和约束、充分性要求、通过准则、备注等）走结构化列，便于搜索与比对。
- 纯文本快照写入 `plain_text`，供列表摘要与搜索使用（沿用需求正文块口径）。
