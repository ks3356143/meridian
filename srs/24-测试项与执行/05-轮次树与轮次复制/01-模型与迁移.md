# 模型与迁移

> 返回 [轮次树与轮次复制入口](../05-轮次树与轮次复制.md)

## 一、目标数据结构

```text
test_rounds
  └─ test_item_folders(round_id)
       └─ test_items(round_id)
            ├─ test_sub_items
            ├─ test_cases(test_item_id)
            │    └─ test_case_steps(test_case_id)
            │         └─ content_blocks(owner_type=test_case, block_key=step.{stepId}.op|act)
            └─ requirement_test_items
```

- 文件夹也必须带 `round_id`。否则第 2 轮修改文件夹会反写第 1 轮，无法满足“整树独立”。
- `test_cases`、`test_case_steps` 不增加 `round_id`；通过父测试项/用例继承轮次，避免三份真相。
- `content_blocks` 不增加 `round_id`；步骤复制后产生新 `stepId`，`op/act` 自然按新步骤隔离。
- 附件文件不复制，`assetId` 可跨轮复用。

## 二、表结构变更

| 表 | 变更 | 约束 / 说明 |
| --- | --- | --- |
| `test_rounds` | 保留现有字段 | `source_round_id` 表示第二轮及以后的基准轮来源；`round_type` 保留内部枚举 `initial` / `regression`，分别对应“首轮 / 后续轮”，不作为用户可见文案；不复制历史轮本身 |
| `test_item_folders` | 新增 `round_id NOT NULL` | 索引 `(round_id, type_code, parent_id, sort_order)`；父目录必须同轮 |
| `test_items` | 新增 `round_id NOT NULL`、`lineage_key NOT NULL` | 唯一 `(round_id, identifier)`；索引 `(round_id, type_code, folder_id, sort_order)` |
| `test_cases` | 新增 `lineage_key NOT NULL` | 删除项目级标识唯一约束；唯一 `(test_item_id, identifier)` |
| `test_case_steps` | 新增 `lineage_key NOT NULL` | 唯一 `(test_case_id, lineage_key)`；序号仍在用例内唯一 |
| `test_sub_items` | 不加轮次字段 | 通过 `test_item_id` 继承轮次；随测试项复制 |
| `requirement_test_items` | 不新增轮次字段 | 每个轮次测试项复制一条关联，仍指向同一需求 |
| `content_blocks` | 不改表结构 | 复制 `sub_item.*.ops/exp` 与 `step.*.op`；不复制 `step.*.act` |
| `round_test_items` | 迁移后删除 | 现有实现中的中间表，不再使用 |
| `round_test_cases` | 迁移后删除 | 现有实现中的中间表，不再使用 |
| `static_test_workbenches` | 暂不纳入本方案 | 静态专属继承规则待确认，禁止在复制逻辑中静默丢弃 |

### 稳定标识建议

建议给测试项、用例、步骤各加一个 `lineage_key`：

- 第 1 轮：`lineage_key = 现有记录 id`。
- 后续轮复制：保留源 `lineage_key`，内部 `id` 全部生成新的 UUIDv7。
- 用户可见 `identifier` 也在轮间保持一致；唯一性按轮或父实体收敛。
- 上轮记录、历轮对比、文档追溯均通过 `lineage_key + 轮次`定位，不靠名称、序号或人工标识猜测。

若不采用 `lineage_key`，至少要在复制时保存来源项/用例/步骤 ID，否则当前轮改名、调序后就无法稳定找到上轮对应记录。

## 三、迁移步骤

当前本地库实测：`test_items=6`、`test_cases=5`、`test_case_steps=3`、`step.*.act=2`、`round_test_items=0`、`round_test_cases=0`，两个项目各有第 1 轮。

推荐“短停机 + 一次性迁移”，不做双写：

1. 停止后端和所有写入操作，复制一份 SQLite 数据库备份。
2. 预检每个有测试数据或文件夹的项目都存在第 1 轮；缺失时先由 Go 生成 UUIDv7 补建。
3. 预检 `round_test_items`、`round_test_cases` 必须为空；非空时中止迁移并输出明细，不静默丢弃。
4. 按 SQLite 官方表重建流程新增 `round_id` / `lineage_key` 和新的唯一约束；依赖表外键在迁移期间关闭，迁移后执行 `foreign_key_check`。
5. 将现有测试项、文件夹全部归入所属项目 `round_number=1` 的轮次；现有测试项、用例、步骤 ID 保持不变。
6. 现有 `content_blocks` 中的 `step.*.act` 原样保留在第 1 轮，不清空、不重写 `block_key`。
7. 生成新的 lineage 值：第 1 轮测试项/用例/步骤使用自身 ID。
8. 删除空的 `round_test_items`、`round_test_cases`。
9. 核对各表行数、外键、孤立块和唯一约束，重启后端。

### 停机判断

需要停机。原因是 SQLite 单写者模型、需要重建 `test_items/test_cases` 约束并删除旧范围表；在线迁移会让正在执行的请求读到半迁移结构。当前数据量很小，预计是秒级维护窗口，但不能用“数据少”代替备份和回滚演练。

## 四、迁移风险

- `test_items` 是多个表的外键父表，重建顺序错误可能级联删除用例、步骤、子项或静态工作台。
- 现有 `UNIQUE(project_id, identifier)` 会阻止跨轮同标识复制，必须迁移掉。
- 现有桥表若在未知环境中有数据，不能直接删除；当前库为 0，但迁移必须预检。
- 第 1 轮内容块依赖原步骤 ID；只要第 1 轮保留原 ID，现有实测结果无需迁移。
- 静态测试项若只复制基础行、不处理 `static_test_workbenches`，会产生“看起来存在但工作台为空”的伪完整状态。

## 五、迁移验收

- 所有存量测试项和文件夹的 `round_id` 均指向本项目第 1 轮，无空值。
- `test_items`、`test_cases`、`test_case_steps`、`content_blocks` 行数与迁移前一致。
- 现有 `step.*.act` 的 owner、block_key、body_json 哈希不变。
- `PRAGMA foreign_key_check` 为空。
- 创建第 2 轮后，第 1 轮任意对象的更新不影响第 2 轮，反之亦然。
