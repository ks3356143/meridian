## 一、模块实测基线（2026-09-29，R2657 真实数据 + 425 行拦截夹具）

| 事实 | 数值 |
| --- | --- |
| 进入需求与追踪一次性拉全量快照 | `GET /api/v1/projects/{id}/requirements` 返回 `sources + sections + requirements`，**每条需求含完整 `description`** |
| 真实载荷（29 条需求 / 149 章节） | **110.9 KB**，其中描述正文 **38.9 KB（35%）** |
| 单条成本 | 平均 **2097 B**/条（描述平均 494 字，最长 1248 字） |
| 真正的卡顿主因 | 右侧候选表未虚拟化：317 行 ≈ 6300 单元格常驻 DOM。A/B 实测：**保留表格时树滚动 77ms/帧，隐藏表格后 17ms/帧** |

结论：正文不能进列表契约，图片不能 base64 内联，正文不能存 HTML 字符串。100 KB 级纯文本的 `JSON.parse` 不是瓶颈（1–2ms），但富文本化之后会立刻变成主因。量级外推与全局规则见 [全局契约](../23-数据加载与渲染性能.md)。

## 二、全页交互性能追加（2026-09-29，生产构建）

### 已完成
- `AppProviders` 只挂一个 Radix `TooltipProvider`；`Tooltip` 不再每实例包 Provider；`TruncatedText` 只在 `open` 时挂 `TooltipContent`，关闭态不再常驻 Portal/Popper。
- 共享 `DataTable` 行拆成 `memo(DataTableRow)`，并传入 `renderVersion = table.options.columns`；列定义变化时强制行重渲染，避免动态勾选/操作单元格被 memo 住。
- `RequirementsTree`、`RequirementsCandidateTree`、`RequirementsHero`、`RequirementDetail`、`RequirementsCandidateWorkbench`、`ReceivedAssetTable` 按数据/状态 props memo；候选工作台表格 props 使用模块级常量稳定化。
- 一级导航去掉 `flushSync` 和 `mousedown` 双触发，改为 `startTransition` 更新切换占位。
- `LazyChunkBoundary` 捕获候选 chunk 加载失败并局部重试；需求布局模块变更时开发模式整页失效，避免 HMR 保留旧 lazy 引用；非活动面板 `inert` 隔离键盘/读屏；Tooltip 退出动画用 mounted 延迟 140ms 卸载。
- 需求页 Tabs 根容器改为单格 Grid；候选面板用 React `lazy` + `Suspense` 拆成独立 chunk，候选 TAB 的 `pointerenter` / `focus` / `pointerdown` 预加载；首次激活用 `useTransition` + `QueryLoading` 骨架兜底。面板可见性由与 `workbenchTab` 同一次紧急更新提交的 `panelsReady` 控制，重内容仍等 `candidateActivated` transition 提交后才展示；两个面板常驻网格、切换只切可见性。

### 实测（R2657 真实 29 条，Edge 144Hz，生产预览 4173）
| 交互 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 首次进入待确认 TAB | 2 次长任务 / 最大 139ms | 骨架 16ms 可见，57ms 长任务后 109ms 出表；之后切换 0 |
| 点击待确认表格行 | 78ms | 0 |
| 打开解析 SRS 弹窗 | 77ms | 0 |
| 切回已确认 TAB | 61ms | 0 |
| 进入批量编辑 | 59ms | 0 |
| 表格滚动 | 0 | 0 |

首屏 LCP 约 76ms、0 长任务，候选 tree/workbench chunk 不在首屏请求；首次激活 fallback 16ms 可见，57ms 长任务后 109ms 出表，之后切 TAB、点行、解析弹窗、切回、批量编辑全部 0 长任务。

### 边界与后续
- `5173` 开发服务器仍受 React 19 development 构建的 `ProfileMode` 和 Vite 模块图影响，打开 F12 会更重；**性能验收只看 4173 生产预览**，开发服务器只验证功能。
- 首屏已无长任务；候选首次激活仍有 57ms 长任务但由骨架覆盖。要彻底消除首次激活 TBT，需要 Step 3 的按章节分页/分块渲染，而不是继续增加预加载。
- 双面板 TAB 首次切换时，`panelsReady` 必须与 `workbenchTab` 同批提交，禁止先渲染“已切到候选页但旧面板仍 `display:none`”的中间态，否则旧 TAB 上的 Tooltip reference 会瞬间变成 0×0 并飘向左上角；`workspaceTabs` 随 `workbenchTab` 重建只作为辅助，不能单独解决；TAB Tooltip 同时启用 `hideWhenDetached` 兜底。
- Tooltip 关闭时 Content 立即卸载，退出动画会缩短；若必须保留完整退出动画，改用 Presence 延迟卸载，不得恢复每单元格 Provider。

## 三、Step 1 实施记录（2026-09-29）

### 已落地契约
- 列表：`RequirementResponse` 的 `description` 使用 `omitempty`，Workbench 列表映射统一清空正文，只下发 `descriptionExcerpt`（按 rune 截断 80 字并加省略号）和 `hasDescription`；创建、更新单条响应仍保留完整正文，避免复制和失焦保存需要二次请求。
- 详情：新增 `GET /api/v1/software-requirements/{id}/content`，返回 `id / description / hasDescription / updatedAt`；详情面板、候选编辑弹窗、回收站复制都在打开时按 id 请求。
- 搜索：新增 `GET /api/v1/projects/{code}/requirements/search?q=&sourceVersionId=`，服务端匹配章节号、名称、标识、描述和标签，只返回 `id / fields / excerpt`；前端 220ms debounce，TanStack Query `keepPreviousData`，候选表格额外保留来源文档名、版本和 sourceAnchor 的本地匹配。
- 表格：候选审阅表“原文描述”列直接渲染服务端 80 字摘要，移除 `TruncatedText` 和 hover Tooltip，不挂 Portal，不再把完整正文放进表格渲染管线。
- 加载态：详情和候选编辑的正文请求用延迟 250ms 才显现的骨架槽（CSS animation-delay），避免本地快速请求闪烁；错误态可重试。

### 实测（R2657 真实 29 条，生产预览 4173）
- Workbench 响应：110.9 KB → 78.5 KB（剔除 38.9 KB 正文后仍含 sources/sections）；列表 JSON 中不再出现 `description`。
- 详情内容请求：约 760 B / 8 ms；候选编辑弹窗打开后 description 完整长度 102 字，0 长任务。
- 服务端搜索：`外部接口` 853 B / 5 ms，`指令` 9.4 KB / 5 ms；候选表格筛选命中 2 条，测试期间 0 长任务。
- 工作区内部切到需求与追踪：0 长任务；候选 TAB 预热后切回再切出：0 长任务。直接整页刷新仍有应用启动阶段的 chunk 解析长任务，需与页面数据加载区分。
- 构建拆包：把 `@tanstack/query-core` 固定拆到 `vendor-query` chunk，避免新增服务端搜索 hook 后 Rollup 把共享查询运行时并进入口 `index`；入口 gzip 116.33 KB，与 Step 1 前基线持平，原始体积只增加约 2.7 KB。

### 当前边界
- 搜索接口当前按项目读取需求后在 Go 内过滤，1000 条纯文本规模可接受；Step 3 做章节分页时改成 SQL LIKE/FTS 或游标查询，避免把搜索结果全量留在前端。
- 正文仍是纯文本；结构化正文、图片资源化、块级虚拟化属于 Step 2，尚未开始。

## 四、DataTable 组件审计（2026-09-29）

### 结论
表格没有手搓引擎：列、排序、行模型和虚拟化分别由 `@tanstack/react-table` v9、`@tanstack/react-virtual` 和 shadcn/ui Table 提供；项目自定义的只是业务列、单元格内容和项目视觉胶水。审计后保留 TanStack + Virtual + shadcn 组合，不替换为 AG Grid/MUI DataGrid。

### 本次删改
- `DataTable` 从单文件拆为 `data-table.tsx`（虚拟化与组合）、`data-table-header.tsx`（表头/排序）、`data-table-row.tsx`（行渲染/memo/键盘激活）、`data-table-types.ts`（列元数据与响应式类），职责边界清晰。
- 删除无调用方的 `rowClassName`、`virtualized.height`、`virtualized.overscan`；虚拟化只保留 `rowHeight`，默认 overscan 固定为 8。
- 删除章节列上的死 `meta.width`：该字段没有任何消费方，章节列宽实际由 `requirements-candidate-workbench.module.css` 的 7.5rem 规则控制。
- 使用 TanStack v9 官方 `columnMeta: metaHelper<DataTableColumnMeta>()` 声明列元数据类型，去掉两处 `as DataTableMeta` 断言，`hiddenUntil` 现在有类型校验。
- `leftAlignedColumns` 统一归一化成一个按签名缓存的 `Set`；调用方传内联数组（如 `[1]`）时不再每轮生成新引用，避免 `memo(DataTableRow)` 被整体击穿。

### 保留的自定义边界
- 排序表头 UI：TanStack 只提供排序状态和 handler，不提供 UI；继续使用 shadcn Button + lucide 排序图标。
- 行键盘激活：TanStack 不负责 `<tr>` 的 Enter/Space 语义，保留小组件内的键盘处理。
- 选中色条、空态、响应式隐藏、批量选择状态：属于业务/视觉胶水；批量选择跨筛选、跨树联动，继续放在调用方而不是塞进表格引擎。
- spacer 行：使用 TanStack Virtual 官方窗口化模式，不是自研虚拟滚动算法。

### 验证
- `npm run check` 通过；生产构建入口 gzip 保持 116.33 KB，未因拆分增加首屏体积。
- 生产预览 4173 验证候选表：章节三态排序、20 行摘要、单行勾选与已选计数、行点击激活并联动左侧树、虚拟滚动容器均正常。
- 生产预览验证非虚拟化项目表：正常渲染、行点击进入项目详情，证明共享组件两条路径都可用；控制台 0 Error。

## 六、Step 2 方案（2026-09-29 确认）

全局契约见 [数据加载与渲染性能](../23-数据加载与渲染性能.md)，外部引擎能力与选型见 [技术路线 · 外部文档引擎](../03-技术路线.md)。

### 已定决策

1. **解析依赖 OfficeCLI 的结构抽取，Go 保留兜底**：DOCX 进块走 `view outline`（骨架 + heading 层级 + 段落号）、`get <tbl> --depth N`（表格行列）、`query picture`（图片路径 + `relId` + 宽高）；OfficeCLI 不可用或解析失败时降级到现有 Go 纯文本解析，主链路不中断。
2. **图片二进制按 `relId` 从 docx 压缩包直读 `word/media/*`**，由 Go 完成；`get --save` 只作为调试兜底（74 张图用 `--save` 要起 74 个进程，不可接受）。
3. **富文本编辑面分阶段**：Step 2 先做只读块渲染 + 轻量结构化编辑（段落 / 标题 / 列表用 autosize 文本域，表格与图片用专用块组件）；确需行内格式时再挂富文本编辑面。编辑器选型与调研结论见 [内容块模型 · 编辑器选型调研](../15-内容块与附件模型/01-内容块模型.md)。

### 四个切片

| 切片 | 内容 | 验收 |
| --- | --- | --- |
| 1 | 块模型定稿（只写文档）：`heading` / `paragraph` / `list` / `table` / `image` / `pagebreak`；识别不了的块降级为 `paragraph` 且不丢内容 | ✅ 已完成（[需求正文块模型](./06-需求正文块模型.md)）；存储采用 `content_blocks`（`owner_type=requirement`），节点白名单 13 项已定稿 |
| 2 | DOCX → 块 + 图片资源化（后端）：骨架索引 + 按需取块 + 图片落 assets 表 | ✅ 已完成：迁移 0017/0018、受限块校验、`/software-requirements/{id}/blocks` 读写、OfficeCLI 客户端、媒体抽取与资源登记、导入管线、**解析 SRS 时按章节区间逐需求落正文块**（引擎不可用时降级为纯文本并在解析提示中标注）；真机端到端联调通过 |
| 3 | 前端块渲染 + 块级虚拟化：长文档虚拟化、图片进视口解码、宽高比占位不跳布局 | 生产预览无布局跳动，滚动无长任务 |
| 4 | 生成侧打通：`merge` / `dump` + `batch` 写模板，`validate` 做门禁，`view screenshot` 做生成后自动视觉验收 | 生成文档 schema 校验通过 + 截图与模板基线一致 |

### 两级解析策略（避免"解析一个大文档卡 20 秒"）

- **一级（解析入库时）**：`view outline` 拿骨架、统计与 heading 层级，把段落号映射到需求条目（6.1MB 文档实测 349ms）。
- **二级（打开详情时）**：只取该条需求涉及的表格 `get --depth N`（实测 350ms/表），1–3 次调用约 1s，由加载态兜底。
- 图片：解析时一次 `query picture` 拿到全部图片的位置 / `relId` / 尺寸（74 张实测 423ms），二进制按需从 zip 取。

### 风险

1. OfficeCLI 的 JSON 字段没有版本稳定性承诺：用到的字段要写成契约测试，升级必跑（见技术路线的升级回归规则）。
2. `query` / `view` 等只读命令也会拉起 resident 进程并保持，集成时必须显式 `close <file>` 收尾，否则文件被锁。
3. 矢量图（EMF / WMF）等前端无法直接显示的图片格式需要转换或降级占位，实施时确认。
4. 麒麟 V10 可用性未验证，属于前置条件。
