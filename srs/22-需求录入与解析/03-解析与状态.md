# 解析与状态

> 返回 [需求录入与解析](../22-需求录入与解析.md)

## 自动解析与确认

1. 自动解析只生成候选需求，不得直接写入正式需求基线。
2. 章节识别优先使用 Word 标题样式和多级编号；无样式的显式 `1.1 标题` 仅作为兜底，目录样式、表格内段落和日期/版本号不得生成章节。
3. 标题形如 `[RQGN001-XXX-001] 名称` 的叶子功能识别为候选需求，外部标识写入需求外部标识字段；其下“子功能概述 / 输入信息 / 业务处理需求 / 输出信息”合并为该叶子需求描述，不单独生成候选。
4. 功能需求组之外的章节仅当标题包含“功能 / 需求 / 要求 / 约束”且描述含“应、须、确保、能够”等规约词时生成候选，降低背景、术语和文档说明误报。
5. 自动解析把全书目录写入章节表；重解析只清理“原文中已不存在且无子节点、无需求引用”的解析章节，手工章节和已有需求引用章节保留。作业面由需求状态动态推导，不删除全文参考目录。
6. 表格第一阶段只保留 `[表格]` 占位，图片保留 `[图片]` 占位；后续升级为结构化表格、图片资产和原文锚点。
7. 候选确认页使用左树右表：左侧为需求章节链，右侧为候选需求表。
8. 候选需求必须展示原文片段或原文上下文，便于判断解析是否漏项、重复或误把说明文字识别为需求。
9. 用户可逐条或批量确认、排除、合并、拆分、修改后再确认。
10. 确认后的候选需求进入正式需求基线；排除项保留排除结果，避免下次重复解析时反复出现在待确认列表。
11. 自动解析不得阻塞手动录入；两种路径可以并行使用。

## 需求状态

状态用于隔离未确认内容、保留审计和支撑版本演进，不是为了增加用户管理负担。日常界面只在必要位置展示状态。

| 状态 | 用途 |
| --- | --- |
| 候选 | 自动解析产生，尚未人工确认。 |
| 正式 | 人工录入保存后，或候选需求确认后，进入当前有效需求基线。 |
| 已排除 | 人工判断不是软件需求、重复或不应采纳；保留排除记录，避免重复识别。 |
| 已替代 | 新 SRS 版本采纳差异后，旧版本需求退出当前基线，但保留历史追踪。 |

版本差异中的新增、删除、描述变化、章节移动、性质变化是比对结果，不落成新的需求状态。界面用差异标签展示，用户采纳后才写入对应版本基线。

## 自动创建测试项

1. 需求保存或确认为正式需求后，系统默认自动创建关联测试项。
2. 需求与测试项采用多对多追踪；自动创建策略、测试项名称、标识、挂载位置和类型映射在测试项模块设计时确定，不得在需求侧硬编码一对一限制。
3. 测试项模块尚未实现前，本条只作为需求侧契约记录：需求保存不得因测试项能力未落地而失败，必须保留自动创建意图或待执行关系。
4. 后续实现测试项模块时，必须补齐自动创建结果、失败重试和需求与测试项的追踪关系。
5. 来源需求被排除后，需求与测试项关系保留。测试项列表、统计入口、详情和追踪矩阵必须提示“来源需求已移出基线”，报告生成预检将其列为风险；完全没有需求来源的测试项另行提示“无来源需求”并提供筛选。
