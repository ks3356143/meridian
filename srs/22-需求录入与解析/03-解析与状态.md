# 解析与状态

> 返回 [需求录入与解析](../22-需求录入与解析.md)

## 自动解析与确认

1. 自动解析只生成候选需求，不得直接写入正式需求基线。
2. 章节识别优先使用 Word 标题样式和多级编号；无样式的显式 `1.1 标题` 仅作为兜底，目录样式、表格内段落和日期/版本号不得生成章节。
3. 解析候选以原文章节为最小需求单元：一个识别为需求的章节生成一条候选需求，除第 5 条外部接口口径外不做自动合并、拆分或聚合。标题形如 `[RQGN001-XXX-001] 名称` 的叶子功能识别为候选需求，外部标识写入需求外部标识字段；其下“子功能概述 / 输入信息 / 业务处理需求 / 输出信息”作为该章节候选的描述内容。
4. 功能需求组之外的章节仅当标题包含“功能 / 需求 / 要求 / 约束”且描述含“应、应当、须、需要、确保、能够、至少、不低于、不高于、质量要求”等规约词时生成候选，降低背景、术语和文档说明误报。候选审阅界面不得提供合并或拆分操作；用户只能修改、确认或排除候选章节。候选需求主类型由章节标题判定：标题含“性能/响应时间/处理时间/运行周期/内存/吞吐/时延/延迟”判性能，含“接口/通信/总线/协议”判接口，含“安全/保密/权限”判安全，含“可靠/冗余/故障/恢复”判可靠，其余默认功能；描述中出现的时间、接口、故障等实现词汇不参与类型判定。
5. 第三方测评口径下，仅标题明确为“外部接口 / 对外接口”的章节生成一条接口候选；泛化“接口”和“内部接口”不生成候选。外部接口的子章节和表格上下文合并进该候选描述；若外部接口下已有显式 RQGN 叶子需求，则显式叶子优先。外部接口候选应携带“外部接口”标识。
6. 自动解析把全书目录写入章节表；重解析只清理“原文中已不存在且无子节点、无需求引用”的解析章节，手工章节和已有需求引用章节保留。作业面由需求状态动态推导，不删除全文参考目录。
7. 表格第一阶段只保留 `[表格]` 占位，图片保留 `[图片]` 占位；后续升级为结构化表格、图片资产和原文锚点。
8. 候选确认页名为“待确认需求”，使用左树右表：左侧为需求章节链，右侧为候选需求表。
9. 候选需求必须展示原文片段或原文上下文，便于判断解析是否漏项、重复或误把说明文字识别为需求。
10. 用户可逐条或批量确认、排除、修改后再确认；不提供合并和拆分能力。
11. 确认后的候选需求进入正式需求基线；排除项保留排除结果（状态为已排除），避免下次重复解析时反复出现在待确认列表。重解析按设计保留已排除记录、不重建候选：解析完成提示中的“保留已排除 Z 条”即该语义，命中已排除章节时计入该数字而不是漏判。
12. 排除可逆，统一由“需求回收站”管理：已排除的候选需求可“撤回排除”回到待确认队列（excluded -> candidate，章节作业面随之恢复），支持单条与勾选批量撤回；曾进入基线的已删除确认需求可“恢复确认”回到正式基线（excluded -> official）。撤回与恢复按最新 exclude 事件的来源状态决定目标状态，恢复前执行章节、名称和标识冲突检查。
13. 彻底删除只针对曾进入正式基线的已删除确认需求；候选排除记录不提供彻底删除——物理删除会让下次解析重新生成该章节，绕过“排除记忆”的设计。候选排除记录在回收站中的勾选框禁用，也不参与批量彻底删除。
14. 自动解析不得阻塞手动录入；两种路径可以并行使用。

## 需求状态

状态用于隔离未确认内容、保留审计和支撑版本演进，不是为了增加用户管理负担。日常界面只在必要位置展示状态。

| 状态 | 用途 |
| --- | --- |
| 候选 | 自动解析产生，尚未人工确认。 |
| 正式 | 人工录入保存后，或候选需求确认后，进入当前有效需求基线。 |
| 已排除 | 人工判断不是软件需求、重复或不应采纳；保留排除记录，避免重复识别。 |
| 已替代 | 新 SRS 版本采纳差异后，旧版本需求退出当前基线，但保留历史追踪。 |

版本差异中的新增、删除、描述变化、章节移动、性质变化是比对结果，不落成新的需求状态。界面用差异标签展示，用户采纳后才写入对应版本基线。

## 需求创建测试项

1. 需求保存或确认为正式需求后**不自动创建测试项**；创建动作必须由用户在需求详情「关联测试项」中显式触发，避免保存动作隐式写业务数据。
2. 需求详情提供「创建并关联测试项」区块，位置在基础信息之后、长正文之前；默认名称取需求名称，类型按主类型映射（功能 `SU`、接口 `IO`、性能 `AC`、安全性 `SE`、可靠性 `KK`，其他默认 `SU`），优先级为「中」，标识后缀自动生成，文件夹、充分性要求、通过准则和测试项描述使用类型默认值；静态类型 DC/SA/CR/CW 不参与。
3. 创建与关联在同一事务内完成；正式需求、需求归属和描述完整度必须由服务端校验。描述待补全的需求禁用入口，不能通过接口绕过。
4. 当前需求已有任一关联测试项时，再次点击先确认“已有关联需求，是否创建一个新的关联测试项？”；取消不写数据，确认后跳过同类型同名称复用，创建新的关联测试项并自动调整标识后缀。未有关联时的重复提交仍按同需求 + 同类型 + 同名称幂等处理；不同测试项类型可分别创建，保持多对多关系。
5. 首个关联建立后需求 `test_item_task_status` 变为 `completed`；来源需求被排除后，需求与测试项关系仍保留。测试项列表、统计入口、详情和追踪矩阵必须提示“来源需求已移出基线”，报告生成预检将其列为风险；完全没有需求来源的测试项另行提示“无来源需求”并提供筛选。
6. 批量创建提供两种入口：需求 Hero「一键创建测试项」检查全部已确认需求；需求树批量编辑栏「创建测试项」检查勾选需求。两者共用 `POST /api/v1/projects/{code}/test-items/from-requirements`，服务端逐条复用单条创建规则，默认跳过已有关联测试项和待补描述需求，返回创建 / 跳过 / 失败汇总；前端只展示检查范围，不以 `test_item_task_status` 预判创建数量，结果以服务端真实关联关系为准。
7. 测试项 TAB 同样提供「从已确认需求创建测试项」入口：`GET /api/v1/projects/{code}/test-items/from-requirements/preview` 返回可创建 / 已关联 / 待补描述状态、映射类型与阻塞原因，弹窗默认展示可创建项，并支持搜索、筛选、全选当前可创建项和逐条结果回看。预览与创建共用同一资格口径：正式需求且正文非空才可创建；空正文始终拦截，`test_item_task_status` 只作兼容字段，不作为放行条件。候选列表使用虚拟滚动，创建成功后刷新需求候选、测试项工作台与详情，并选中第一条新建测试项。

## 通用 DOCX 解析经验

### 基础策略

1. `.docx` 本质是 ZIP 包，正文读取 `word/document.xml`。不要把 XML 整体读成字符串后用正则拆内容；使用流式 XML decoder 处理段落、表格和嵌套元素，避免大文档占用过多内存。
2. 解析粒度先保留段落序号。每条章节、候选或证据都记录 `DOCX 段落 N` 一类原文锚点，方便后续回溯和调试。
3. 段落解析要跟踪：`w:p` 段落、`w:pStyle` 样式、`w:numPr / w:numId / w:ilvl` 自动编号与层级、`w:t` 正文、`w:tab` 转空格、`w:drawing` 记录 `[图片]` 占位、`w:tbl` 进入表格层级。
4. 表格内段落第一版不要直接当正文或标题，统一降级为 `[表格]` 占位，避免版本表、日期表、参数表误生成章节或需求。
5. 图片只保留 `[图片]` 占位，第一版不把图片资产写入解析结果。

### 标题与章节

1. 优先识别 Word 标题样式；无样式但满足 `1.1 标题` 形态的显式编号只作为兜底。
2. 目录、日期、版本号、页眉页脚不是章节；表格内段落、句号、日期格式的短文本不能因为行长短就识别成标题。
3. `1`、`Heading 1`、`标题 1` 等写法先归一化大小写，再按结尾数字或专用映射推导层级。
4. 使用 Word 多级自动编号时，显式编号可能不在标题文本里，应根据样式层级维护章节计数器，不要假定 `w:t` 中一定有 `1.2.3`。
5. 全书章节写入章节表以保留原文目录和上下文；是否生成业务候选由文档类型和专项规则决定。

### 验证经验

1. 解析器规则用 Go 单元测试覆盖，构造段落或最小 OOXML 夹具，不依赖真实项目数据。
2. 每类新文档至少覆盖：正常章节、目录干扰、表格干扰、嵌套层级、边界标题、应生成的候选、不应生成的候选。
3. 专项规则写清文档来源和业务口径，例如“外部接口才是第三方测评需求”是测评业务规则，不是通用文本规律。
4. 涉及界面展示时，用浏览器截图检查标识、列宽、Tooltip 和换行，不要只用 DOM 文本判断视觉结果。

### 当前坑位

- 表格内日期、版本号或短文本被当成章节：表格内段落一律不生成章节，先保留 `[表格]` 占位。
- Word 样式标题重复编号或章节号错位：优先用样式和多级编号推导层级，避免把标题文本编号重复拼进数据。
- 背景说明、接口表格行被误判成需求：普通章节必须同时满足标题特征和规约词；特殊类型必须由标题和业务口径明确授权。
- 重解析后已有候选状态或人工判断丢失：只替换 `parsed + candidate`，保留 `official / excluded / superseded` 及审计记录。
- 质量类章节未生成候选：规约词标记集至少覆盖“应、应当、须、需要、确保、能够、至少、不低于、不高于、质量要求”。
- `inferPrimaryKind` 把功能需求误判成性能/接口/可靠性：主类型判定只用章节标题，描述只用于“是不是需求”的判定和原文展示；改动用真实 DOCX 离线回放验证类型分布，并补标题判定单元测试。
