# 技术路线

## 成熟方案选型铁律

- 遇到通用交互、动画、虚拟滚动、表格、路由、数据请求、文件解析、Word 渲染等能力时，先检查项目内已有封装，再核对官方文档和主流生态的成熟组件或库；默认不手搓核心算法、状态机和复杂动画时序。
- 候选方案必须与当前技术栈兼容：前端需适配 React 19、Tailwind CSS 4、shadcn/Radix、深浅主题、无障碍和 reduced motion；后端优先 pure Go、可测试、可 Windows 与麒麟 V10 携带运行。
- 成熟方案之间出现取舍时，优先选择维护活跃、API 官方明确、侵入性更小、与现有架构更一致的一项；不盲目叠加功能重复的依赖。
- 手写仅限业务编排、视觉适配，或成熟生态确实缺少对应能力的局部补齐；实施前必须在对应 SRS 记录不用成熟方案的原因、手写边界和验证口径。

## 外部文档引擎（OfficeCLI）

**定位：外挂引擎，不是核心依赖，也不做常驻服务。** 业务数据、正文权威源和存储仍然由我们自己的 SQLite + 受限 JSON 内容块承担；OfficeCLI 只负责「把 OOXML 搬对、校对、渲染出来」这一段。

### 承担的三件事

1. **模板合并**：用 `merge`（模板 + JSON 替换 `{{key}}` 占位）和 `dump` / `batch`（子树序列化成可回放命令再批量写入）生成文档，避免手写 Go 去重建编号、样式继承、页眉页脚、合并单元格这类高风险版式。
2. **Schema 校验**：生成后用 `validate` 做 OpenXML schema 校验，作为文档预检的第一道门禁。
3. **DOCX 页面预览**：用 `view --render html` / `view screenshot` 把 docx 渲染成 HTML 或按页 PNG，由后端生成并缓存为静态产物，前端只消费产物；渲染产物是预览，不是生成中间格式。

### 边界（必须守住）

- **不参与业务语义解析**：把 SRS 读成章节号、需求条目和类型判断仍由 Go 完成；OfficeCLI 只给文档 DOM 与 XML，不解释业务口径。
- **不参与数据存储**：正文权威源仍是 SQLite 中的受限 JSON 内容块，图片仍按 `assetId` 进资源表；OfficeCLI 不写我们的数据库。
- **不进入生成链路**：继续保持「不采用通用 HTML 转 OOXML」的结论，`view html` 只做预览产物。
- **不常驻**：不走 resident 命名管道、不做 HTTP 服务，只按需一次性子进程调用。
- **失败可降级**：OfficeCLI 不可用时，文档生成与预检退回 Go 原生渲染路径，主链路不得因此不可用。

### 集成约定

- Go 侧用 `os/exec` 一次性调用；多步操作合并成一次 `batch`，摊薄每次约 250ms 的进程启动成本。
- 输入输出一律走临时目录 / 缓存目录，产物落盘后再由 Go 读取入库或作为静态资源提供。
- 必须设置执行超时、输出大小上限和失败清理，禁止无超时等待外部进程。
- **后端进程必须能找到引擎**：设置环境变量 `OFFICECLI_BINARY=<绝对路径>`，或把 `officecli` 放进 PATH；两者都缺时解析自动降级为纯文本，并在解析完成提示中标注"正文块未生成"。

### 版本与更新

- **每次会话开工或要求打开前后端时，必须检查并更新 OfficeCLI**：`npm view @officecli/officecli version` 对比本机 `officecli --version`；有更新就升级到最新稳定版。升级后过一遍 `officecli --help`、`officecli help <docx|xlsx|pptx>` 和本地 skill 文件，把新增命令与快捷能力记回本文件。
- 接入文档生成链路后，每次升级都必须补跑保真度回归（真实模板 dump → 回放 → `validate` → 截图对比），回归不过就回退版本。
- 本机当前版本 1.0.152，安装位置是 CherryStudio 的 mise 工具链（配置项 `"npm:@officecli/officecli" = "latest"`），Codex MCP 指向该副本；若改用 `npm install -g` 单独安装，必须同步把 MCP 指向改过去，避免两份版本不一致。

### 实测能力（2026-09-29，真实交付文档）

| 需要的能力 | 命令 | 实测结果 |
| --- | --- | --- |
| 块类型与标题层级 | `view <file> outline` | 456 段落 / 53 表格 / 75 图片，并给出 heading 1–3 层级树；349ms |
| 表格行列 | `get <file> /body/tbl[1] --depth 6 --json` | 17 行 × 3 列，单元格文本完整（含空格子） |
| 图片位置与尺寸 | `query <file> picture --json` | 74 张；给出文档路径、`relId`、宽高（如 15.0cm × 7.2cm） |
| 图片二进制 | `get <file> <picture path> --save x.png` | 导出 146KB 真 PNG（magic `89504E47`） |
| 页面预览 | `view <file> html` | 125KB 模板 → 466KB 自包含 HTML（`lang="zh-CN"`），2.1s |
| 全文档克隆脚本 | `dump <file> / -o full.json` | 6.1MB 文档 → 11.8MB 可回放脚本，4954ms（是「写」用的克隆脚本，不是「读」用的树） |

**标题与编号能力（2026-09-29 实测）**

| 问题 | 谁解决 | 实测结论 |
| --- | --- | --- |
| 标题层级识别 | OfficeCLI + Go | `get` 返回 `style: "heading 2"` / `styleId` / `styleName`；`view outline` 给出 heading 1–4 层级树 |
| 样式继承的有效值 | OfficeCLI | `effective.font.eastAsia` 等有效值带 `src` 来源（`/styles/2`、`/docDefaults`），手写解析很难做到 |
| 编号定义 | OfficeCLI | 段落级 `numId` / `numLevel` / `numFmt` / `listStyle` / `start`；`/numbering` 下有 `lvl` 的 `ilvl` / `start` / `numFmt` / `pStyle` / `lvlText`（如 `%1.`） |
| 编号数值（1.2.3 这类） | **Go 自己算** | `view outline` / `view text` / `view annotated` **都不展开自动编号值**；必须按 `lvlText` + 文档顺序自增 / 重置计算，现有解析器的章节计数器继续用 |
| 题注 / 交叉引用 / TOC | OfficeCLI | 支持 `field`（SEQ / REF / PAGEREF / STYLEREF / DOCPROPERTY / IF）与 `toc` 元素；`refresh` 重算页码需 Windows + 已安装 Word |

真实文档里自动编号是重灾区：软件详细设计说明 1369 个 `numPr`、第三方测试报告 1673 个，模板类文档 48–98 个 —— 编号必须按「定义靠 OfficeCLI、数值靠 Go」的分工处理。

**排版规则能力（字体 / 字号 / 缩进，2026-09-29 实测）**

| 交付要求 | 对应属性 | 实测结论 |
| --- | --- | --- |
| 表格内五号字（10.5pt） | `size=10.5pt` | ✅ 可读可写，官方 help 即以 `size=10.5pt` 为例；真实模板表格里读到 `size.cs=10.5pt` |
| 中文宋体 + 西文 Times New Roman | `font.ea=宋体` + `font.latin="Times New Roman"`（写 ascii + hAnsi）+ `font.hint=eastAsia` | ✅ 分槽字体原生支持；真实模板读到 `font.ea=黑体` 等值 |
| 正文小四（12pt） | `size=12pt` | ✅ 真实模板正文段落实测 `size=12pt` |
| 正文首行缩进 2 字符 | `firstLineChars=200`（1/100 字符单位） | ✅ 实测 4 个真实段落 `firstLineChars=200 / firstLineIndent=24pt`，并支持属性选择器 `query 'p[firstLineChars>0]'` 批量筛选 |

同一套属性体系还覆盖：行距（`lineSpacing=1.5x` + `lineRule`）、两端对齐（`align=justify`）、段前段后（`spaceBefore` / `spaceAfter`）、跨页控制（`keepNext` / `keepLines`）、语言标记（`lang.ea=zh-CN` / `lang.latin=en-US`）、上下标（`vertAlign`）、按字符的挂起缩进（`hangingChars`）。

**三个实测坑**：

1. **字号分两个槽**：`size`（`w:sz`）与 `size.cs`（`w:szCs`）。真实模板出现「只有 `size.cs=10.5pt`、没有 `size`」的情况，读字号必须两槽同看，否则会误判为未设字号。
2. **`firstLineChars` 不支持在 `add` 中设置**（help 标注 `[set/get]`）：新建段落需「先 add 段落、再 set 字符缩进」两步。
3. **五号 / 小四 / 四号不是 API 概念**，需自建号数→pt 映射（五号 10.5、小四 12、四号 14、小五 9）；`firstLineChars` 的实际宽度随字号变化，校验时必须读 `firstLineChars` 本身，不能用换算出的 pt 反推。

**由此新增的能力：排版 lint。** 生成文档后用属性选择器批量断言（如筛出所有 `firstLineChars` 不等于 200 的正文段落、表格内字号不是 10.5pt 的单元格），生成违规清单作为交付门禁 —— 以前只能人工翻页或用 Word 宏。与 [七类文档数据映射 · 版本预检与约束](./17-七类文档数据映射/03-版本预检与约束.md) 衔接。
**路径陷阱（实测）**：`view outline` 的 `[N]` 是**全文档 `w:p` 顺序号（含表格内段落）**，与 DOM 路径 `/body/p[N]`（只数 body 直属段落）**不是一回事**（例：outline `[126]` 的「测评环境」对应路径 `/body/p[79]`）。定位必须用 `paraId` 或 `query`，禁止拿 outline 序号直接当路径。

**读 / 写命令分工**：读结构用 `view outline` / `query` / `get --depth N`；写与克隆用 `dump`（导出可回放脚本）→ `batch`（回放写入）。取图片二进制优先按 `relId` 从 docx 压缩包直接读 `word/media/*`，`get --save` 作为调试兜底。

**运维坑（2026-09-29 多次实测）**：

1. `query` / `view` 这类只读命令也会自动拉起 resident 进程并保持，导致文件被锁、删除失败；集成时必须显式 `close <file>` 收尾（文件被 resident 持有时 `create` 返回 `file_locked`）。
2. **写入延迟落盘**：resident 生效期间磁盘上仍是旧内容，非 officecli 程序（含我们自己的 Go 代码）读文件前必须先 `save` 或 `close`，否则读到的是修改前的版本——联调时踩过一次，表现为"解析出来是空文档"。

### OOXML 能力来源选型（2026-09-29 调研）

结论：**Go 生态没有可用的完整 OOXML 读写库**，这正是引入 OfficeCLI 的直接原因。

| 库 | 星 | 许可 | 最近更新 | 判定 |
| --- | --- | --- | --- | --- |
| unidoc/unioffice | 4936 | 商业 EULA，需 license code | 2026-09 | ❌ 需付费授权 |
| officecli/officedex | 1067 | GPL-3.0 | 2026-09 | ❌ 传染性许可 |
| sajari/docconv | 1792 | MIT | 2024-07 | ⚠️ 纯 Go，但只转纯文本，无表格 / 图片块结构 |
| mattn/docx2md | 766 | 无 LICENSE 文件 | 2026-07 | ❌ 默认版权保留，不可用 |
| nguyenthenguyen/docx | 620 | MIT | 2024-07 | ⚠️ 只做占位符文本替换 |
| fumiama/go-docx | 306 | AGPL-3.0 | 2025-05 | ❌ 传染性许可 |
| lukasjarosch/go-docx | 280 | MIT | 2024-07 | ⚠️ 只做占位符替换 |
| gomutex/godocx | 270 | MIT | 2025-08 | ✅ 纯 Go 读写，但已停更、能力偏生成 |
| mmonterroca/docxgo | 124 | MIT | 2026-08 | ✅ 活跃，声称读改写保样式 + 模板合并 + 表格 / 图片 / 域，但社区规模小 |

选型规则：

1. **不把完整 OOXML DOM 库作为核心依赖**：免费的只到「模板替换」级别，能力最全的是商业授权；唯一活跃的 MIT 候选星标只有百级、单人维护，不适合压在交付链路的必经路径上。
2. 确需引入 Go 库时，**首选 `mmonterroca/docxgo`、次选 `gomutex/godocx`**，且只在一个受控场景试用，用真实交付模板跑「读 → 改 → 存 → 与 OfficeCLI 渲染截图对比」通过后再扩大使用面。
3. 现有流式 XML 解析器继续保留：它负责**业务语义解析**（章节、需求、类型），这部分任何库都替代不了。
4. 版式搬运、表格 / 图片结构抽取、渲染与校验交给 OfficeCLI。
### 前置验证（未完成前不作为实现依据）

1. **麒麟 V10 可用性**：官方只声明 macOS / Linux（glibc、musl）/ Windows，未声明麒麟，需实测。
2. 中文与东亚排版保真：字体槽、自动编号、页眉页脚、合并单元格、目录与域。
3. `refresh`（重算 TOC / 页码）需要 Windows 且已安装 Word，客户机器不一定具备。
4. 真实交付模板的 dump → 回放 → 截图对比回归。
5. 分发方式：Apache-2.0 可随包分发（需带 LICENSE / NOTICE）；官方二进制来自 `d.officecli.ai`，发布包内必须固定到已验证的具体版本并校验 SHA256。

## 版本要求

依赖版本跟随当前最新稳定版。每次会话开工或要求打开前后端时，必须检查全部依赖库更新，后端明确包含 Huma v2、GORM、SQLite 驱动等，前端包含 React、Vite、React Router、Tailwind、TanStack、Radix 和构建工具等；有更新时先升级并更新锁文件，完成对应构建或依赖一致性验证后再启动或重启。React Router 相关包必须保持同一版本，TypeScript 使用当前最新稳定版。不能使用 `--force` 掩盖依赖冲突；最新版本与当前技术栈或运行环境不兼容时，保留最新兼容版本并记录原因。

本次会话使用的 skills 只在下班时检查更新状态并提醒用户决定由谁更新，不自动升级。
