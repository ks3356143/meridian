# 大工作区重设计讨论

## 状态

- 本文件记录大工作区从 0 重设计的会话需求、讨论顺序和待确认问题。
- 当前阶段只做需求与信息架构讨论，不修改业务代码。
- 本文件是讨论底稿；经确认的结论后续回写到《11-首页与项目导航》《14-项目工作区与前端模块》《07-前端体验》，避免多处重复维护。

## 讨论顺序

1. 先定义主任务：项目在不同阶段下，用户进入工作区后最优先完成的动作是什么。
2. 再定信息架构：一级导航如何分组、二级导航归属哪些模块、轮次上下文放在哪里。
3. 再定工作区壳：顶部 Cockpit、一级导航、内容区、状态反馈和移动端折叠方式。
4. 再定首屏状态：编制大纲中、大纲已评审、测试执行中、回归验证中、报告编制中分别默认展示什么。
5. 再定视觉稿级布局：信息密度、层级、模块色、卡片质感、动效和 reduced-motion 边界。
6. 最后定实施切分：先落地壳与导航，再按业务模块逐个替换占位页。

## 已有硬约束

- 工作区是独立全屏路由，不显示系统后台左侧导航。
- 项目详情是只读状态驾驶舱；工作区是作业面，两者不得混用职责。
- 工作区按模块拆分路由与组件，不做单个巨型页面。
- 交互组件优先使用 shadcn/ui、Radix UI、TanStack Table 等成熟组件库。
- 全局视觉与动效必须符合《07-前端体验》；具体工作区布局细节确认后回写《14》。
- 需求先确认再实现；本次讨论期间不动代码。

## 核心待确认问题

1. 一级导航形态：横向 TAB、左侧窄导航、顶部两级导航，还是按阶段动态重组？
2. 阶段自适应：编制阶段是否只展示“下一步任务流”，评审后是否切换为“执行总览”？
3. 轮次上下文：全局轮次切换器保留在顶栏，还是进入轮次模块后才切换？
4. 信息密度：工作区偏舒适工程风，还是偏高密度作业台？
5. 常驻信息：项目状态、安全等级、风险摘要、生成预检、当前用户，哪些必须始终可见？
6. 布局基线：桌面端是否固定为“顶栏 + 一级导航 + 模块内容区”，内容区内部再由各模块自定？
7. 移动端策略：一级导航折叠成抽屉、底部 TAB，还是保留精简横向滚动？

## 整体大分层

用户 2026-09-13 提出的项目主分层：

1. 模板层：提供默认模板；项目可选择模板，模板影响界面录入层。
2. 界面录入层：承接用户录入、编辑和作业流。
3. 数据层：保存单一来源数据、过程数据、关联数据、专项数据等多种数据类型，并可继续细分。
4. 生成文档层：从数据和模板生成 Word。

建议补充的横向或支撑层：

| 层 | 职责 | 说明 |
| --- | --- | --- |
| 过程编排层 | 阶段、轮次、任务流和默认入口 | 决定“当前该做什么”，避免界面模块平铺后失去主线。 |
| 校验与预检层 | 录入校验、生成预检、完成度口径 | 同一套规则服务界面提示、完善度统计和文档生成阻断。 |
| 追溯与影响域层 | 文档、需求、测试项、用例、问题、回归之间的关系 | 是回归范围和报告结论的依据，不只是展示矩阵。 |
| 导入与回流层 | 接收 DOCX、比对采纳、研制方反馈回流 | 服务项目启动、评审修改和问题归零，不与生成层混在一起。 |
| 附件与证据层 | 文件、图片、大规模数据集登记 | 管理原始证据和资产，不把文件内容直接塞进业务正文。 |
| 权限与配置层 | 用户、项目成员、操作边界、字典 | 保证项目隔离和角色能力，不让页面自行判断权限。 |
| 运行支撑层 | 存储、迁移、日志、备份、构建部署 | 本地绿色版的基础能力，独立于业务域。 |

暂不单独分层：

- 统计汇总：由数据层派生，生成文档层消费，先作为能力而不是独立层。
- 前端状态：属于界面录入层内部的 view model，不上升为全局架构层。
- API 层：是各业务域对外的边界表达，不作为跨所有业务的单一平面层。

### 分层方法讨论

1. 正交分层：技术栈、数据生命周期、过程状态、文档输出是四个不同维度，不强行叠成一个上下级关系。
2. 定义-实例-快照：需求、测试项、用例等项目级定义跨轮稳定；轮次实例承接范围和执行；文档生成固化输出快照。
3. 数据契约：每类数据声明拥有者、生命周期、版本策略、校验规则和 Word 槽位；模板通过注册表影响界面，不直接让界面解析模板。
4. 投影式界面：工作区页面是“过程状态 + 数据完善度 + 追溯关系”的投影，页面本身不做权威计算。
5. 导入导出适配：外部 DOCX 导入和 OOXML 导出都围绕统一领域模型转换，不互相直连。

### 分层口径收敛

2026-09-13 用户进一步收敛：

- 模板层指真实 DOCX 中可定制的内容，例如标题段落、数据来源、字体样式等。
- 非固定数据由界面录入层承接；录入大头是测试项和用例。
- 测试项结构看测评大纲中的测试项表格；用例结构看测试记录中的用例表格。
- 最终交付为 7 类基础文档加 2N 份轮次文档，具体计数规则待后续确认。

## 用户真实作业主线

2026-09-13 用户口述的项目主线：

1. 新建项目。
2. 接收并登记依据文件，例如《XXX软件需求规格说明》《XXX软件研制任务书》，这些文档是后续需求分析和测试项设计的主要来源。
3. 编制测评大纲：围绕大纲上下文、静态测试和动态测试组织测试项。
4. 外部评审后修改大纲。对工具而言，这一步不改变主流程本质，仍表现为大纲版本、评审意见和修订记录，最终仍生成 Word。
5. 编制测试说明：一般把测试项中的每个测试子项作为一个用例。
6. 填写测试记录。
7. 发现问题后记录问题单。
8. 问题、需求和用例发生变化时，生成第二轮测试说明，填写影响域，再填写第二轮测试记录。
9. 如仍有问题，继续第 X 轮测试说明、第 X 轮用例与测试记录。
10. 最终汇总生成测评报告。

### 阶段模型读法

- 大阶段采用：测评大纲编制 -> 大纲外部评审修改 -> 测试说明编制 -> 测试记录填写 -> 问题归零与回归 -> 测评报告。
- 回归不是独立一次性阶段，而是“第 2 轮至第 X 轮”的可重复循环；每轮都包含说明、记录、问题与影响域。
- 静态测试与动态测试是测评大纲编制和轮次阶段里的两个明确分野，不是普通测试类型的并列展示。
- 外部评审主要影响大纲版本与修订说明，不应把后续录入流程卡死。

## 两份大纲阅读结论

### 通用模板《测评大纲.docx》

- 主章节覆盖：范围与标识、测评依据、测评性质、测评目的、时间地点、测评对象及环境、测评要求内容及方法、评价方法、问题类别等级、通过准则、度量数据、暂停恢复终止、组织分工、保障、安全保密和附录。
- 附录承担大量固定表格：文档审查单、代码审查单、静态分析审查单、需求与测试需求对照表、问题报告单。
- 静态测试环境与动态测试环境是 5 章的一级分野，各自包含环境描述、软件项、硬件固件项和场所；动态环境另有测评数据与环境差异性分析。
- 测试项及方法在 6.2 汇总，具体测试项通常以结构化表格输出。

### BCD 星真实大纲

- 依据文件分三类：标准 / 管理文件、研制任务书、需求规格说明等被测软件文档，并记录名称、标识、日期和来源。
- 测试策略明确：先做文档审查、代码审查、静态分析，静态问题闭环后再进入动态测试。
- 真实项目从软件需求规格说明、研制任务书和隐含需求整理出 16 个需求，再分析出 34 个测试项；其中静态 3 个：文档审查、静态分析、代码审查，其余为功能、性能、接口、边界、人机交互、安全性、余量、强度、恢复性、安装性、兼容性等动态类型。
- 测试项在 6.2 下按测试类型和功能域形成层级，每个测试项用固定表格承载：测试项名称、测试项标识、优先级、追踪关系、需求描述、测试项描述、测试方法、充分性要求、通过准则。
- 测试项描述中的编号如 `XQ_SU_ZMFY_SU01` 已经体现“测试子项 -> 用例”的自然关系；测试说明阶段可把每个测试子项展开为一个用例。
- 附件包含测试项与软件需求规格说明对照表，用于证明测试需求覆盖软件需求。

## 对大工作区设计的直接影响

1. 工作区首屏应围绕阶段主线组织，而不是简单展示 9 个并列模块。
2. 大纲编制期的核心页面应是“依据文件 -> 需求分析 -> 测试项树 -> 大纲上下文完善”的作业链。
3. 静态 / 动态分野必须在信息架构中显性表达：大纲阶段分开设计环境与策略，执行阶段先静态闭环再动态。
4. 测试项详情应使用与真实大纲一致的结构化字段，并为“测试子项一键生成用例”提供明确入口。
5. 测试说明不是从零填写，而是从当前轮范围中的测试项与测试子项推导生成。
6. 回归轮创建时必须带出问题、需求变化、用例影响域，并允许人工确认范围。
7. 文档产出区应按阶段显示当前待生成对象：大纲、第 1 轮说明 / 记录、问题单、第 N 轮回归说明 / 记录、测评报告。
