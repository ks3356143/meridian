# 轮次与追溯模型

## 核心定义

一轮测试是一份测试说明、一份测试记录和一组本轮执行数据的组合。轮次不是所有业务数据的父节点，而是测试范围和执行数据的快照上下文。

项目创建成功后在同一事务中自动创建第 1 轮，初始状态为 `draft`。项目列表可显示项目状态，项目状态与轮次状态分开维护。

## 数据所有权

| 层级 | 数据 | 规则 |
| --- | --- | --- |
| 项目级 | 项目基础、相关方、人员、依据文件、被测对象、静态环境、时间锚点、需求树、测试项逻辑定义。 | 全轮共享，不随轮次复制。 |
| 轮次级 | 动态环境、测评数据、差异分析、软件更改、轮次范围、执行记录、本轮新问题。 | 每轮独立，修改不影响历史轮和已生成文档。 |
| 逻辑层 | 需求、测试项、用例的稳定标识和追溯关系。 | 跨轮保持同标识，用于历轮汇总。 |
| 实例层 | 某轮纳入的测试项、用例及其执行结果。 | 只归属当前轮，可从逻辑定义生成。 |

## 轮次模型

`test_rounds` 核心字段：

- `id`、`project_id`
- `round_number`：项目内从 1 连续递增。
- `name`：默认“第 N 轮”，允许修改。
- `round_type`：`initial` / `regression`。
- `status`：`draft` / `ready` / `executing` / `closed`。
- `started_on` / `ended_on`
- `dut_version`
- `dynamic_test_location`
- `change_reason`：`problem_fix` / `requirement_change`
- `reason_summary`
- `source_round_id`：回归轮的基准轮。
- `created_at` / `updated_at`

唯一约束：`project_id + round_number`。删除轮次仅允许删除未生成文档的草稿轮，后续以归档为主。

轮次起因只有问题修复和需求变更两类。“软件出了新版本”是更改的结果，不作为单独建轮原因。一轮只对应一个被测件版本；版本升级链由各轮 `dut_version` 组成。

## 轮次基线与阶段

每轮保存输入基线：被测软件版本、需求等技术文档版本、专项数据集版本、测试设计和静态 / 动态阶段状态。回归轮更改分析从上一轮基线推导。

`round_stages` 表示静态测试和动态测试阶段，保存状态、时间、执行范围和门槛检查。项目策略可要求静态问题闭环后再启动动态测试。

## 测试项与用例两层模型

### 类型与文件夹字典

`test_item_types` 是全项目唯一类型字典，字段包含：类型代号、展示名、静态 / 动态分类、军标输出顺序、适用平台、默认测试方法和是否系统内置。DC、SA、CR、CW 等静态类型由系统预置；功能、性能、接口等动态类型按字典输出，不在前端硬编码。

类型字典同时声明测试项后缀和用例序号的长度、字符集与唯一性作用域。后缀可以是 4 到 6 位，不把“固定 4 位”写死在通用模型里。

`test_item_folders` 保存项目级文件夹树，与测试项使用同一容器排序规则，支持文件夹和测试项在同容器内穿插排序。轮次范围带入测试项时，同步生成轮次文件夹快照或记录快照路径，保证历史轮文档树不漂移。

### 逻辑定义

- `test_items` 保存项目级测试项逻辑定义：稳定标识、名称、类型、优先级、测试方法、充分性要求、层级和排序。
- `test_sub_items` 保存测试项内的测试子项或方法项，包含稳定标识、名称、需求描述、方法描述和预期要点，可推导建议用例。
- `test_cases` 保存项目级用例逻辑定义：稳定标识、名称、综述、初始化、前提约束、通过准则、设计人员和步骤定义。
- 需求与测试项、测试项与用例的追溯关系挂在逻辑层，跨轮不变。

### 轮次实例

- `round_test_items` 表示某轮纳入的测试项范围，可记录轮次内排序、文件夹快照、来源和备注。
- `round_test_cases` 表示某轮纳入和可能修改过的用例实例，保存轮次内步骤快照、来源类型和执行信息。
- 来源类型：`reuse` / `modified` / `new`。
- 回归轮带入的实例保持原稳定标识；新增项生成新的稳定标识。
- 执行记录只挂轮次用例实例，不直接改写逻辑定义。

## 静态审查数据

文档审查单、代码审查单、静态分析检查单和质量度量数据独立建模：

- `review_checklists` 保存版本化审查模板。
- `review_results` 保存项目、轮次、受审对象、检查项、结果、备注和证据。
- `quality_metrics` 保存注释率、模块规模、圈复杂度、扇出数、缺陷率等静态分析或汇总指标。
- 审查单输出由审查模板和结果组装，不在 Word 渲染器里硬编码检查项。

## 回归范围默认规则

第 N 轮（N ≥ 2）默认范围：

1. 上轮未通过用例及其所属测试项。
2. 上轮问题单影响域关联的测试项，其下用例默认全选。
3. 需求或被测对象变化关联的测试项，作为提醒项供人工勾选。
4. 测试人员自由追加或移除，最终范围以人工确认结果为准。

新建轮次向导分三步：范围勾选、轮次数据继承策略、版本和时间信息。默认动态环境、测评数据、差异分析沿用上一轮，可切换为空白新建。

## 轮次内容继承

- 沿用上一轮时，深拷贝对应 `content_blocks` 的 `body_json` 和 `payload_json`，不共享对象。
- 附件文件不复制，实例节点继续引用同一 `assetId`。
- 软件更改部分不自动继承，回归轮手动填写。
- 第 1 轮也包含环境差异性分析。
- 时间推导重算时，仅覆盖未人工锁定的推导值。

## 需求追溯

链路为：

```text
来源文档 → 需求 → 测试项 → 用例 → 执行记录 → 问题单
```

- 需求树项目级唯一，不复制到轮次。
- 需求详情显示关联测试项和历轮执行结论。
- 测试项详情显示来源需求、用例覆盖和历轮结果。
- 当前轮视角下，需求树按当前轮实例自底向上显示；切换“全部”时显示全量逻辑树。
- 需求符合情况默认按历轮结果推导，允许人工覆盖并记录覆盖原因。

## 缺陷与报告单

- 缺陷 `issues` 归属发现轮，不跨轮携带实体。
- 对外报告单 `issue_reports` 是独立载体，可聚合多个缺陷；统计时区分缺陷数和报告单数。
- 缺陷可关联多个用例实例，并保存影响域关联的测试项逻辑 ID。
- 回归结果在后续轮填写，回归日期必须落在回归轮时间窗口内。
- 最后一轮仍有未闭环重大或严重问题时，工作台显示“缺少回归轮次”风险。
- 待回归工作台按当前轮展示上轮未闭环缺陷、关联用例和回归填写入口。

## 完善度口径

轮次完善度至少统计：

- 环境与数据块填写情况。
- 测试范围是否确认。
- 用例定义必填项。
- 未执行用例原因。
- 未通过用例是否建单。
- 问题单处理和回归信息完整性。

统计由后端统一计算，前端只展示，不在多个组件内重复推导。
